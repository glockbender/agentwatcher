# Процессы агентов

Здесь — как приложение находит живого агента по его процессу, когда хуков нет, что для этого
читает у Claude Code, как держат свои сессии десктопные приложения, Claude.app и ChatGPT.app, и как
отправитель узнаёт запуск без окна. Чего здесь нет: как строка, найденная по процессу, переживает перезапуск —
[session-recovery.md](session-recovery.md); куда ведёт клик по ней —
[session-focus.md](session-focus.md).

## Почему живой агент находится только у Claude

Приложение показывает строку и для агента, о котором не слышало ни одного хука: живой процесс
агента — это сессия, даже если приложение было выключено, когда она началась. Такая строка
строится из процесса и держится на двух свойствах, а есть они только у Claude.

Первое — счёт. Один процесс `claude`, запущенный человеком, — это одна сессия (служебные процессы
самого агента сюда не входят: [«Агент работает, а приложение о нём не слышало»](session-recovery.md#агент-работает-а-приложение-о-нём-не-слышало)). У Codex десктопное приложение держит
много тредов в одном процессе, поэтому по процессу нельзя сказать даже, сколько там сессий, не
говоря о том, какая из них какая.

Второе — ключ склейки. Хук Claude несёт номер своего процесса (`AgentWatchSendMain`), и по этому
номеру строка, построенная из процесса, отдаёт своё место настоящей сессии, когда та наконец
подаёт голос. Хуки Codex не несут номера процесса ни в каком виде, поэтому найденная по процессу
строка Codex стояла бы рядом с настоящей сессией вечно — два ряда об одном агенте.

Отдельный случай — **фоновая сессия**: Claude Code запускает её сам, в pty под `claude bg-pty-host`,
и над ней нет ни терминала, ни приложения — дерево процессов упирается в `launchd`. Отправитель
узнаёт это по дереву процессов — сам агент или один из процессов Claude над ним является помощником
агента, `bg-pty-host` или `bg-spare`, названным словом или флагом (`claude bg-pty-host …` в одной
сборке, `claude --bg-pty-host …` в следующей; замерено на 2.1.269 и 2.1.270) — и сообщает третий вид
хоста, `background` вместо `cli` (замер: Claude Code 2.1.269, 2.1.270). Спрашивается это только у
процессов, запущенных программой самого
агента: слова помощников обычные, и предок, запущенный с ними по своим причинам (`emacs --daemon` —
обычный способ запустить Emacs, а терминал внутри него родитель всего, что там набирают), иначе
объявил бы фоновой самую обыкновенную сессию. Так же выглядит сессия, которую человек отправил в фон
командой `/bg`: супервизор продолжает её копией `claude --fork-session --resume <транскрипт>` под
`bg-pty-host`. Для копии отправитель добавляет в каждый хук поле `forked_from_session_id` —
идентификатор исходной сессии, прочитанный из аргумента `--resume` (`-r`, `--resume=…`) процесса
агента и отредактированный так же, как `session_id`, — и виджет продолжает строку исходной сессии, а
не заводит вторую ([«Сессию отправили в фон»](session-recovery.md#сессию-отправили-в-фон)). Поле ставится только для
сессии, чей `session_id` совпадает с `--session-id` процесса: тот же процесс сначала проживает
заглушку, которую оставляет `--resume`, и её хуки исходную не называют. Сканер живых процессов
спрашивает у дерева процессов тот же вопрос, что и отправитель, поэтому строка копии, построенная до
первого хука, тоже фоновая. Помощников сканер при этом пропускает, но хуки от них приходят: прогретая
заготовка `bg-spare`, которую демон отдаёт виду агентов, шлёт обычные `SessionStart` и `SessionEnd`,
и строку такая сессия получает не на старте, а на первом признаке работы
([«Сессию отправили в фон»](session-recovery.md#сессию-отправили-в-фон)). Виджет по нему не ищет окно: клик по строке открывает новую вкладку
Ghostty с `claude attach <job id>`. Идентификатор задания берётся из записи самого Claude Code о
процессе, `~/.claude/sessions/<pid>.json` — там же лежат вид сессии (`interactive` или `bg`), её имя
и `bridgeSessionId` для Remote Control; файл замерен, не документирован ([«Фоновая
сессия»](session-focus.md#фоновая-сессия)) (замер: Claude Code 2.1.269).
Документация Claude Code называет такие файлы внутренними и предлагает вместо них `claude agents
--json` (поля `cwd`, `kind`, `id`, `state`, `pid`, `status`, `sessionId`, `name`). Приложение всё
равно читает файл: команда стоила бы запуска процесса на каждый клик и зависела бы от `PATH`
человека. Пересмотреть, если файл перестанет читаться.

Терминал, в котором набрали `/bg`, при этом не освобождается, что бы ни говорила документация:
замерено на 2.1.269, интерактивный процесс `claude` остаётся жить, в его записи реестра появляется
`parkedJobId` с идентификатором задания, он единственный интерактивный процесс с соединениями к
демону Claude Code, а размер его терминала совпадает с размером pty фоновой сессии (замер: Claude
Code 2.1.269). Сессия показана
в этой же вкладке, отдельного `claude attach` нет. Приложение читает все записи
`~/.claude/sessions/*.json` и называет зрителем живой интерактивный процесс, чей `parkedJobId` равен
`jobId` копии; пока он жив, строка выглядит и кликается как терминальная, а его выход возвращает
строку в вид `background` ([«Сессию отправили в фон»](session-recovery.md#сессию-отправили-в-фон)). Что процесс тот
самый, а не новый под выданным заново номером, проверяется по времени запуска из той же записи:
`procStart` — время по ядру в UTC в написании `ps -o lstart` (`Sat Sep 12 09:53:31 2026`), а в
записи без него `startedAt` — миллисекунды с 1970 по часам Claude Code, на восьми замеренных записях
на 0–3 с позже ядра (замер: Claude Code, версия не записана).
Сбрасывает ли Claude Code `parkedJobId`, когда человек возвращается из сессии в список агентов, не
замерено.

Запись пропадает, когда процесс выходит сам: так было с двумя процессами после сброса вывода их
закрытых терминалов (замер: Claude Code 2.1.270, 2.1.280). Остаётся ли она после аварийного выхода,
не замерено. Узнавание по записи от этого не зависит — его держит сверка времени запуска.

Та же запись отвечает на вопрос, на который не отвечает ни один хук: **ответил ли человек на
диалог.** Поля — `status` (`busy`, `idle`, `waiting`, `shell`), `waitingFor` и `statusUpdatedAt`.
`waiting` стоит ровно пока наверху диалог, ждущий человека, а `waitingFor` называет какой:
`permission prompt` у запроса разрешения, `input needed` у вопроса-выбора, плюс `dialog open`,
`sandbox request` и `worker request` у остальных (замер: Claude Code 2.1.272). Ответ возвращает
запись в `busy` в тот же момент;
замерено на 2.1.272 — диалог открылся в 17:44:59, ответ дан в 17:55:23, `statusUpdatedAt` сдвинулся
ровно на эти 623,8 с (замер: Claude Code 2.1.272). Файл переписывается на месте: inode не менялся ни
на одном из пяти переходов
в трёх сессиях (замер: Claude Code 2.1.272). `statusUpdatedAt` двигается только когда меняется само
слово, поэтому он и годится
как момент ответа, а не как признак жизни.

Приложение читает это единственным способом и ради единственного факта: **ожидание кончилось**.
Зажигает ожидание по-прежнему хук `PermissionRequest` — вместе с тем, кому диалог принадлежит
([«У диалога есть хозяин»](agent-events.md#у-диалога-есть-хозяин)), — гасит запись, и только если статус не `waiting` и `statusUpdatedAt` не старше возраста
строки. Хозяин здесь не проверяется намеренно: запись говорит про всю сессию, и `waiting` в ней
стоит и от диалога сабагента — это замерено на той же сессии, где диалог был не у основного потока
(замер: Claude Code, версия не записана).
Читается запись раз в полсекунды и только пока кого-то о чём-то спрашивают. Запись есть не у каждой
сессии — короткоживущая сессия, поднятая из pty, не получила файла вовсе, — и это, как всё здесь,
fail-open: нет файла, незнакомое слово, нет отметки времени — факта нет, строка живёт как жила.
Решение целиком — [ADR-0010](adr/0010-the-answer-to-a-dialog-comes-from-the-session-record.md).

Соответствие «процесс → файл сессии» не разрешается и у Claude, и это замерено: `claude` не держит
транскрипт открытым, по рабочему каталогу однозначны только 3 процесса из 8, а сессия бывает старше
своего процесса на несколько суток (замер: Claude Code, версия не записана). Поэтому такая строка
знает ровно две вещи — имя каталога, в
котором работает процесс, и время его запуска, — а имя сессии появляется у неё только с первым
хуком.

Номер процесса отправитель добывает обходом предков. Раньше обход прерывался на первом процессе,
путь которого ядро не отдаёт (замерено: у родителя `claude` на этой машине путь как раз не
читается), а после обновления, удалившего версию, таким процессом оказывается сам агент (замер:
macOS, версия не записана). Теперь
обход идёт дальше и останавливается только там, где процесса нет: процесс без пути называется
именем, под которым работает, а своим агент признаётся по записи реестра (подраздел «Путь к
программе называет файл, а не запуск» ниже). Если хук всё же пришёл без номера, приложение не может
связать сессию с найденным процессом, и рядом с сессией недолго стоит вторая строка — до первого
хука, который номер назовёт.

### Терминал закрыли, а агент остался

Замерено 2026-09-22 на Darwin 24.3.0, на двух процессах `claude` этой машины: 2.1.280 во вкладке
терминала PyCharm 2026.2 (вкладку закрыли около 21:55) и 2.1.270 во вкладке GoLand (висел с
14 сентября, беседу тем временем продолжили в новой вкладке через `claude --resume`). Оба живы и
выглядят одинаково (замер: Claude Code 2.1.270, 2.1.280, PyCharm 2026.2, GoLand, macOS 15.3.1):

- в `ps` у агента терминала нет (`??`), а у оболочки над ним состояние `?Es` — она начала выходить
  и не закончила;
- ядро (`sysctl KERN_PROC_PID`): флаг `P_CONTROLT` стоит, устройство терминала `e_tdev` пустое
  (`NODEV`); у всех живых сессий в терминалах есть оба, у PyCharm, GoLand и Finder нет ни одного
  (замер: macOS 15.3.1);
- дескрипторы 0–2 агента по-прежнему открыты на `/dev/ttysNNN`, и PyCharm держит обе стороны этого
  терминала — `/dev/ptmx` с тем же номером и сам `/dev/ttys012` (замер: macOS 15.3.1);
- главный поток агента стоит в `tcsetattr` → `ioctl` (`sample <pid>`) у обоих процессов: агент ждёт,
  когда терминал примет его вывод, чтобы поменять режим терминала (замер: Claude Code 2.1.270,
  2.1.280);
- сам Claude Code ничего не замечает: запись `~/.claude/sessions/<pid>.json` говорит
  `status: idle`, `claude agents --json` показывает оба процесса как `interactive`, `idle` (замер:
  Claude Code 2.1.270, 2.1.280).

**Воспроизведение.** Открыть pty, запустить в нём `zsh -il` и набрать `claude` (в доверенном
каталоге, иначе всё съест диалог доверия); затем держать управляющую сторону pty открытой, ничего из
неё не читать и послать оболочке `SIGHUP`. Через 5 секунд агент в том же состоянии — нет терминала,
флаг стоит, поток в `tcsetattr`, оболочка `?Es` (замер: Claude Code 2.1.280). Если вместо этого
просто закрыть управляющую
сторону, агент выходит сам, и случай не воспроизводится. Что именно PyCharm делает при закрытии
вкладки, не замерено; замерено только оставленное им состояние.

**Что его завершает** — на воспроизведении, не на процессах выше:

| Способ | Итог |
|---|---|
| `kill` (`SIGTERM`) | жив через 6 секунд (замер: Claude Code 2.1.280) |
| `kill -9` (`SIGKILL`) | переходит в `?E` — выходит и не может закончить — и так и стоит (замер: Claude Code 2.1.280) |
| `stty -f /dev/ttysNNN flusho` | жив через 8 секунд (замер: Claude Code 2.1.280) |
| `tcflush(TCOFLUSH)` на `/dev/ttysNNN` из другого процесса | выходит через 0,9 с; после `SIGKILL` — через 0,05 с (замер: Claude Code 2.1.280) |

Руками то же делает однострочник на `perl` — он есть в каждой macOS, а в модуле `POSIX` есть
`tcflush`:

```sh
perl -MPOSIX -e 'open(my $t, ">", $ARGV[0]) or die $!; tcflush(fileno($t), TCOFLUSH) or die $!' /dev/ttys012
```

Отсюда два решения приложения. Строку такой сессии оно помечает фазой `TerminalClosed` по паре
«флаг стоит, устройства нет» (`AgentProcessLocator.TerminalState`, [session-model.md](session-model.md#фаза-сессии-и-граф-активностей)), а клик
по ней спрашивает, завершить ли агента, и на «End» делает этот `tcflush`
([ADR-0013](adr/0013-a-click-ends-an-agent-its-closed-terminal-left-behind.md)). Не замерено:
оставляют ли агента так же VS Code и Terminal.app, и получает ли агент при закрытии вкладки PyCharm
`SIGHUP` или что-то другое. Ghostty оставляет агента по-другому — ниже.

**Ghostty: вкладку закрыли, а терминал оставили.** Замерено 2026-09-29 на Ghostty 1.3.1 и Claude
Code 2.1.284, на одном процессе. Человек закрыл вкладку сессии, а через полчаса её `claude` всё ещё
работал (замер: Ghostty 1.3.1, Claude Code 2.1.284). Состояние не такое, как у PyCharm:

- ядро видит всё целым: у агента есть терминал (`ttys024`), флаг и устройство на месте, оболочка и
  `login` над ним живы;
- Ghostty держит управляющую сторону этого терминала (`/dev/ptmx`) и по-прежнему его читает и
  рисует: в `sample` у него пять потоков `io-reader` и пять `renderer`, по одному на каждый из пяти
  терминалов (замер: Ghostty 1.3.1);
- показывает он при этом четыре: этого терминала нет ни в `every terminal` AppleScript, ни в
  полосе вкладок (Accessibility), ни в меню Window. От вкладки осталось окно без рабочего стола —
  такое же остаётся и от вкладок, закрытых как следует (замер: Ghostty 1.3.1);
- агент не висит: его вывод читается, он работает дальше, а ввести в него нечего.

Почему Ghostty не отпустил этот терминал, не выяснено. Другие закрытые вкладки того же Ghostty свои
терминалы отпустили. Отмена закрытия у Ghostty живёт 5 секунд (`undo-timeout`), а этот терминал
держался больше получаса.

Клик по такой строке не должен поднимать окно Ghostty, которое оказалось впереди, — пустую
оболочку в соседнем окне. Строка получает ту же фазу `TerminalClosed`, но найти это можно только у
Ghostty и только при клике. Правило описано в [«Ghostty»](session-focus.md#ghostty), у `GhosttyFocus.decision`. Завершает
такого агента `SIGHUP` — сигнал, который посылает закрытие терминала. Claude Code 2.1.284 отвечает
на него обычным завершением, `shutdown(129)` (замер: Claude Code 2.1.284). Это прочитано в коде и
видно на настоящем случае
2026-09-29: его последний хук `SessionEnd` пришёл в ту же секунду, что и сигнал. Сигнал
получает вся цепочка вкладки: агент, оболочка, из которой его запустили, и `login` над ней — их
находит обход родителей с тем же управляющим терминалом (`AgentProcessLocator.terminalProcessChain`).
Без этого оболочка осталась бы в скрытом терминале, и Ghostty держал бы её до своего выхода.

Не замерено: показывает ли AppleScript Quick Terminal. Если нет, у того, кто им пользуется, Ghostty
всегда держит больше терминалов, чем показывает. То же на 5 секунд после любого закрытия вкладки.
Ни то ни другое само строку не помечает: нужно ещё, чтобы вкладки с именем сессии не было, а имя
другой сессии на вкладке было.

### Путь к программе называет файл, а не запуск

Сканер и отправитель узнают `claude` по пути к его программе, `…/claude/versions/<версия>`
(`ClaudeProcessRules.isClaudeProcess`). Путь дают ядро и `proc_pidpath`, а ядро называет файл, а
не то, как процесс запускали. Замерено на воспроизведении: у файла с двумя именами
ядро называет то, через которое к файлу обратились последним, и называет его всем процессам из этого
файла сразу (замер: macOS 15.3.1). Новая жёсткая ссылка переводит их на новое имя, следующий запуск
по старому возвращает
старое. У файла, от которого не осталось ни одного имени, пути нет (`ENOENT`).

Второе имя даёт сам Claude Code. Хост фоновой сессии (`--bg-pty-host`; хост прогретой заготовки `--bg-spare` этого не делает) заводит
жёсткую ссылку на свою версию в `~/.local/share/claude/ClaudeCode.app/Contents/MacOS/claude`, пишет
рядом `Info.plist` с идентификатором `com.anthropic.claude-code` и текстами разрешений — микрофон,
Apple Events, локальная сеть — и перезапускает себя оттуда: `execve` с `macDisclaimResponsibility`,
переменная `CLAUDE_BG_TCC_DISCLAIMED` (замер: Claude Code 2.1.282). Это прочитано в коде 2.1.282,
запуском не замерено. Зачем —
не документировано; по именам похоже, что разрешения macOS спрашиваются так от имени Claude Code, а
не от имени терминала, который фоновая сессия переживает.

Отсюда были две дыры — и у сканера, и у отправителя, потому что правило у них одно:

- после старта фоновой сессии обычные сессии той же версии выглядят запущенными из пакета, и
  правило пути их не узнаёт. Так выглядела сессия 2.1.272 в `mcp-hub` — обычный `claude --resume`
  во вкладке GoLand, запущенный 15 сентября в 19:52. Каталог `MacOS` в пакете изменён в 22:24 того
  же дня, а когда обновление удалило `versions/2.1.272`, у файла осталось одно имя — в пакете;
- у процесса, чей файл обновление удалило без второго имени, пути нет вовсе. Так остался невидимым
  агент 2.1.270 в той же `mcp-hub`, висевший с 14 сентября.

Обе закрыты одним: процесс признаётся агентом по пути **или** по записи реестра
(`ClaudeProcessRules.isAgentProcess`, `ClaudeSessionRegistry`). Запись пишет сам процесс, и в ней
его время запуска по ядру: на трёх сравненных записях `procStart`
совпал с `ps` до секунды (замер: Claude Code 2.1.270, 2.1.280, 2.1.282). Поэтому запись
засчитывается только в файле своего процесса, с его
номером и со временем запуска, которое сходится с ядром в пределах минуты: номер, выданный заново
чужому процессу, строки не получит. Запись без времени не засчитывается вовсе — здесь ответ строит
строку, а не выбирает окно. Путь остаётся, потому что запись бывает не у каждой сессии, а отсев
помощников агента действует и на узнанных по записи: пишут ли записи `bg-pty-host`, `bg-spare` и
`daemon`, не замерено. После правки сканер нашёл на этой машине те же 11 сессий, что и до неё, и
двенадцатую — агента 2.1.270.

## Десктопные приложения

Замерено 2026-10-07 на Claude.app 2.26454.0 (внутри Claude Code 2.1.289) и ChatGPT.app 26.1002.52244
(внутри `codex` 0.162.0-alpha.2) (замер: Claude.app 2.26454.0, Claude Code 2.1.289, ChatGPT.app
26.1002.52244, Codex 0.162.0-alpha.2). Как перейти к сессии внутри этих приложений — [«Десктопные клиенты»](session-focus.md#десктопные-клиенты).

### Claude.app

Каждая сессия — отдельный процесс Claude Code, который приложение держит у себя:

```text
Claude.app/Contents/MacOS/Claude
  └ Claude.app/Contents/Helpers/disclaimer --pgroup -- <программа>
      └ ~/Library/Application Support/Claude/claude-code/2.1.289/<хеш>/claude.app/Contents/MacOS/claude
          --output-format stream-json --input-format stream-json --setting-sources=user,project,local
          --permission-prompt-tool stdio …
```

Что из этого следует для Agent Watch, по пунктам.

- **События доходят.** Плагин из `~/.claude/skills/agent-watch/` загружается, потому что в
  `--setting-sources` есть `user`. Дошёл и вопрос человеку: ответ на него идёт в окно приложения через
  `--permission-prompt-tool stdio`, но строка получила `userInputRequired` (20:44:41), и запись реестра
  погасила ожидание через 7 секунд (20:44:48, «the dialog is gone») — так же, как в терминале. Каким
  хуком пришёл вопрос, журнал Agent Watch не пишет (замер: Claude.app 2.26454.0, Claude Code 2.1.289).
- **Процесс узнаётся по записи реестра, а не по пути.** Путь не похож на `…/claude/versions/<версия>`,
  и правило пути его не узнаёт. Запись `~/.claude/sessions/<pid>.json` есть у всех четырёх замеренных
  десктопных процессов и пропадает с выходом процесса. В ней два поля, которых нет у терминальных
  сессий: `entrypoint: "claude-desktop"` и `hostSessionId: "local_…"` — идентификатор сессии в самом
  приложении (замер: Claude.app 2.26454.0, Claude Code 2.1.289).
- **Терминала у процесса нет вовсе:** флаг `P_CONTROLT` не стоит (`ps -o flags` даёт `4004`). Пара
  «флаг стоит, устройства нет», по которой строка получает `TerminalClosed`, тут не складывается,
  и ложной пометки не бывает (замер: Claude.app 2.26454.0, Claude Code 2.1.289).
- **Хост — `desktop`, по записи реестра.** До 2026-10-07 `ClaudeProcessRules.clientKind` отвечал
  `cli` всякому процессу без помощника фоновой сессии над ним, и все четыре десктопные строки были
  записаны как `clientKind: cli`: клик поднимал Claude.app со всеми окнами, карточка называла
  сессию терминальной. Теперь `desktop` отвечается, когда запись реестра процесса говорит
  `entrypoint: "claude-desktop"`, — и отправителю, и сканеру. Запись, а не `Claude.app` в дереве
  процессов: `claude`, набранный во встроенном терминале приложения, тоже работал бы под ним, но в
  терминале. Живость такой сессии по-прежнему проверяется по процессу, а не по приложению
  (`desktopBundleIdentifier` у Claude — `nil`): приложение останавливает процессы, оставаясь открытым.
- **Клик открывает сессию в приложении** ссылкой `claude://code/continue?session=<hostSessionId>`
  ([«Десктопные клиенты»](session-focus.md#десктопные-клиенты)).
- **Процесс живёт не столько, сколько сессия.** Приложение запускает процесс, когда сессию открывают
  в боковой панели, ещё до первого запроса, — отсюда `SessionStart` при простом просмотре. Сессию,
  продолжающуюся в новом процессе, оно запускает с тем же `session_id`: сессия `a9afa821…` после
  остановки в 14:50 снова пошла в процессе 20358 под тем же идентификатором и тем же `hostSessionId`,
  и её строка вернулась `SessionStart`-ом (ADR-0002). Архивирование останавливает процесс, и
  `SessionEnd` приходит в ту же секунду. Выход из приложения останавливает все его сессии (замер:
  Claude.app 2.26454.0, Claude Code 2.1.289).
- **Сессия может остаться в приложении без процесса.** Приложение останавливает процесс бездействующей
  сессии: по таймауту простоя (его значение приходит с сервера, по умолчанию выключен), при упоре в
  предел числа процессов и при нехватке памяти (`CliGovernor` в журнале `main.log`). Это прочитано в
  коде; сам такой случай на этой машине не наблюдался: в журнале только `evicted 0 of 0`. Строка
  тогда закрывается, хотя сессия видна в боковой панели и продолжится по первому сообщению (замер:
  Claude.app 2.26454.0).
- **Статус-строки нет**, подтвердил человек 2026-10-07: терминального интерфейса у такого процесса
  нет, а статус-строку рисует именно он. Процента контекста у десктопной сессии поэтому нет — только
  число токенов из транскрипта (замер: Claude.app 2.26454.0, Claude Code 2.1.289).
- **Не видны вовсе** сессии, которые приложение запускает не на этой машине: по SSH, в облаке
  (`cse_…`, `session_…`) и Cowork в виртуальной машине. Их хуки срабатывают там, где они работают.

### ChatGPT.app (Codex)

Бандл тот же, `com.openai.codex`, но приложение называется ChatGPT.app и держит теперь и чат, и
Codex. Треды обслуживает один процесс `codex app-server` из
`ChatGPT.app/Contents/Resources/codex-cli/CodexCLI.app/Contents/MacOS/codex`; путь начинается с
`/Applications/ChatGPT.app/`, поэтому `CodexProcessRules` называет хост `desktop` — так и записан тред,
начатый для замера (замер: ChatGPT.app 26.1002.52244, Codex 0.162.0-alpha.2).

- **События доходят и после обновления до 26.1002.** Перечисление событий в двоичном файле
  0.162.0-alpha.2 (`HookEventsToml` и соседние с ним) — ровно те двенадцать имён, что в каталоге теста
  `testCodexIsAskedForEveryEventCodexOffersAndDeclinesOnlyOnPurpose`, других рядом нет (замер: Codex
  0.162.0-alpha.2).
- **Первый ход нового треда начинается раньше, чем тред попадает в индекс.** В
  `session_index.jsonl` тред записывается, только когда получает имя, через 1,5–3 секунды после
  `SessionStart`. Отправитель пропускает такой тред по первой записи его транскрипта, и строка
  появляется с первым хуком: на двух проверочных тредах `sessionStarted` в журнале Agent Watch
  пришёл в ту же секунду, что `SessionStart`, за 2,9 и 1,5 с до записи индекса, и человек видел
  одну строку ещё до ответа (замер: ChatGPT.app 26.1002.52244, Codex 0.162.0-alpha.2). Как устроен
  допуск — [«Приём сеансов Codex, и открытый вопрос про `/clear`»](agent-events.md#приём-сеансов-codex-и-открытый-вопрос-про-clear).
- **Архивный тред уезжает** в `~/.codex/archived_sessions/`, плоским списком. `TranscriptWatcher`
  ищет только в `~/.codex/sessions/`; клик по строке ищет в обоих местах, потому что ссылке нужен
  идентификатор треда, а он есть только в имени файла.
- **Клик открывает тред в приложении** ссылкой `codex://threads/<id треда>`
  ([«Десктопные клиенты»](session-focus.md#десктопные-клиенты)).

## Запуски без окна

Запуск без окна (по-английски headless) — агент, у которого нет разговора на экране: `claude -p`,
запуск через Agent SDK, `codex exec`. Обычно его начинает программа — скрипт, тест или другой агент
своим инструментом оболочки, — забирает ответ и даёт ему выйти. Отправитель называет такую строку
`headless` (`SessionClientKind.headless`).

**Claude.** Признаков два, и оба спрашиваются у самого процесса агента, а не у процессов над ним:

- `-p` или `--print` среди его аргументов, до `--`;
- `entrypoint` в его записи реестра — `sdk-cli`, `sdk-ts` или `sdk-py`. `claude -p`, запущенный с
  чистым окружением, записал `sdk-cli` и `kind: "interactive"`, так что `kind` запуск не отличает
  (замер: Claude Code 2.1.293).

Аргументы спрашиваются первыми, потому что `entrypoint` — это переменная окружения
`CLAUDE_CODE_ENTRYPOINT`, а дочерний процесс наследует её от родителя: `claude -p`, запущенный
инструментом оболочки сессии Claude.app, записал `claude-desktop` без `hostSessionId` (замер: Claude
Code 2.1.293). Оба признака спрашиваются раньше признаков фоновой и десктопной сессии: над запуском
стоит программа, которая его начала, и иначе `claude -p` из фоновой сессии считался бы фоновым, а
из Claude.app — десктопным (`ClaudeProcessRules.clientKind`). Запуск через SDK внутри сессии
Claude.app не замерен: если SDK не задаёт `entrypoint` сам, запись унаследует `claude-desktop`, и
такой запуск будет выглядеть десктопной сессией.

**Codex.** Признак читается из транскрипта, а не из аргументов: перед словом `exec` могут стоять
параметры со значениями (`-c ключ=значение`, `-p профиль`), и по аргументам слово не найти надёжно.
Первая запись транскрипта `codex exec` говорит `source: "exec"` и `originator: "codex_exec"` при
`thread_source: "user"` (замер: Codex 0.153.4) — [«Приём сеансов Codex, и открытый вопрос про
`/clear`»](agent-events.md#приём-сеансов-codex-и-открытый-вопрос-про-clear).

**Номер процесса у запуска есть и у Codex.** Обычный хук Codex номера не несёт, но `codex exec`
держит один тред и больше ничего, а его хук — дочерний процесс самого `codex exec` или его оболочки
(замер: Codex 0.153.4). Поэтому для запуска отправитель называет ближайший `codex` над хуком, где бы
программа ни была установлена (`CodexProcessRules.headlessRunProcessID`). По этому номеру
приложение следит за выходом процесса, как у Claude: убитый запуск не оставляет строку «работает».
