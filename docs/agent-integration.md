# Встраивание Agent Watch в агентов

Agent Watch ничего не видит, пока не встроен в агента. Здесь собрано всё, что нужно знать про
это встраивание: чем два агента отличаются, куда и как приложение пишет, чего каждый агент
требует и что про них выяснено опытом.

**Почему это один документ, а не по одному на агента.** Почти всё ценное здесь —
сопоставительное. «`Interrupt` есть только у Codex», «доверие требует только Codex», «процент
контекста у Claude берётся из статус-строки, а у Codex из транскрипта» — каждый такой факт
пришлось бы либо задвоить, либо произвольно приписать одному из файлов. Резать по агентам
значит резать поперёк знания.

Общая модель событий, в которую всё это нормализуется, живёт отдельно и намеренно не зависит от
агента — см. [architecture.md, §6](architecture.md).

---

## 1. Чем два агента отличаются

Таблица — вход в остальной документ. Всё, что в ней стоит, ниже объяснено и, где сказано
«замерено», проверено на этой машине.

| | Claude Code | Codex |
|---|---|---|
| куда ставятся хуки | свой каталог-плагин `~/.claude/skills/agent-watch/` | слияние в чужой `~/.codex/hooks.json` |
| плагин, несущий хуки | есть и работает | есть, но хуки в нём не исполняются: `plugin_hooks` в стадии `removed` |
| доверие к хукам | не требуется | **требуется**, по хешу содержимого и позиции записи |
| когда правка доходит | после `/reload-plugins` или новой сессии | со следующего сеанса |
| событий просим | 13 | 11 |
| прерванный ход | хука нет — только чтение транскрипта, до 10 с | `Interrupt`, сразу |
| процент контекста | только из пейлоада статус-строки | приходит записью транскрипта |
| десктопное приложение | нет, живёт в терминале | `com.openai.codex`, делит `~/.codex/` с CLI |
| служебные сеансы | нет | есть, отсекаются по `session_index.jsonl` |
| как узнаётся хост сессии | процесс-предок хука, наблюдение за его выходом | процесс плюс бандл приложения |
| номер процесса в событии | приходит с каждым хуком | не приходит вовсе |
| сессия по живому процессу | находится: один процесс — одна сессия | не находится, см. §1б |

Одна асимметрия стоит того, чтобы назвать её отдельно: `Interrupt` — единственное место, где
Codex богаче. У Claude прерванный ход не порождает ни одного хука, и приложение узнаёт о нём
только чтением транскрипта по тишине; ради этого случая расписание чтения и держит проверку в
покое.

## 1а. Где это живёт в коде

Набор задан данными: `ToolingHooks.hooks(for:)` и `ToolingIntegrations.kinds(for:)` — вся
таблица. Первая говорит, какие события просить у агента, вторая — что вообще можно в него
поставить (у Claude Code это хуки и статус-строка, у Codex только хуки). Третий агент — две
записи в одном файле `AgentWatchCore/ToolingIntegration.swift`.

Окно `Tooling` — проекция этой таблицы, а не список, написанный руками: `ToolingReport.sections`
обходит `AgentSource.allCases`, а каждая строка несёт в себе интеграцию, которой управляет,
поэтому селектора на агента больше нет. Закреплено тестом
`testTheWindowIsAProjectionOfTheAgentsAndTheirIntegrations`: без него агент, добавленный в
таблицу, оказался бы устанавливаемым и невидимым.

У установщика по одной точке входа на операцию — `hookState(for:)`, `installHooks(for:…)`,
`removeHooks(for:)`. Внутри каждой switch по агенту, и это правильно: механизмы действительно
разные — свой каталог у Claude Code против слияния в чужой файл у Codex. Смысл в том, что
switch случается один раз в одном месте, а не у каждого вызывающего.

**Чего в эту таблицу не свели и почему.** Различия в чтении транскрипта, поиске процесса,
разборе имени сессии и значке остались там, где они есть — по одному switch в том месте, которое
про это и знает. Свести их в общий описатель значило бы перенести switch, а не убрать его, и
протянуть один тип через три цели сборки.

## 1б. Почему живой агент находится только у Claude

Приложение показывает строку и для агента, о котором не слышало ни одного хука: живой процесс
агента — это сессия, даже если приложение было выключено, когда она началась. Такая строка
строится из процесса и держится на двух свойствах, а есть они только у Claude.

Первое — счёт. Один процесс `claude`, запущенный человеком, — это одна сессия (служебные процессы
самого агента сюда не входят: `docs/architecture.md` §14). У Codex десктопное приложение держит
много тредов в одном процессе, поэтому по процессу нельзя сказать даже, сколько там сессий, не
говоря о том, какая из них какая.

Второе — ключ склейки. Хук Claude несёт номер своего процесса (`AgentWatchSendMain`), и по этому
номеру строка, построенная из процесса, отдаёт своё место настоящей сессии, когда та наконец
подаёт голос. Хуки Codex не несут номера процесса ни в каком виде, поэтому найденная по процессу
строка Codex стояла бы рядом с настоящей сессией вечно — два ряда об одном агенте.

Соответствие «процесс → файл сессии» не разрешается и у Claude, и это замерено: `claude` не держит
транскрипт открытым, по рабочему каталогу однозначны только 3 процесса из 8, а сессия бывает старше
своего процесса на несколько суток. Поэтому такая строка знает ровно две вещи — имя каталога, в
котором работает процесс, и время его запуска, — а имя сессии появляется у неё только с первым
хуком.

Один изъян есть и у Claude, и он назван здесь, потому что чинить его нечем. Номер процесса
отправитель добывает обходом предков, а обход прерывается на первом процессе, путь которого ядро не
отдаёт (замерено: у родителя `claude` на этой машине путь как раз не читается). Если из-за этого
хук пришёл без номера, приложение не может связать сессию с найденным процессом, и рядом с сессией
недолго стоит вторая строка — до первого хука, который номер всё-таки назовёт. Склеить их без
номера нечем.

Чтобы Codex попал в ту же схему, отправителю Codex нужно научиться сообщать номер процесса CLI —
отдельная работа, а не часть этой.

## 2. Куда приложение пишет

Три места, и обращение с ними разное.

### Claude: свой плагин

Claude Code загружает любой каталог под `~/.claude/skills/`, где лежит
`.claude-plugin/plugin.json`: во всех проектах, без маркетплейса, без шага установки и без
диалога доверия — последний нужен только проектным плагинам из `<cwd>/.claude/skills/`. Плагин
несёт свои хуки в `hooks/hooks.json`.

Поэтому `~/.claude/settings.json` не пишется ни при установке, ни при обновлении, а снятие —
это удаление каталога. Каталог удаляется только если в нём лежит наш манифест: у человека
вполне может быть свой навык с таким же именем, и удалить его значило бы уничтожить чужую
работу, а не снять свою.

Граница механизма: **изменение хуков доходит до запущенной сессии только после
`/reload-plugins` или новой сессии.** Меню обязано это сказать, иначе установка выглядит
несработавшей.

### Claude: статус-строка

Слот статус-строки в Claude Code один и обычно занят. При этом его пейлоад — **единственное
место, где для Claude существует процент контекста**: в транскрипте есть счётчик токенов и нет
размера окна, а таблица «модель → окно» устарела бы молча. Плагин статус-строку задать не
может — из его настроек поддерживаются только `agent` и `subagentStatusLine`.

Чужой скрипт не редактируется ни при каких условиях. Приложение пишет свою обёртку в
`~/Library/Application Support/AgentWatch/`, которая отдаёт копию пейлоада отправителю в фоне и
затем запускает команду человека дословно, пропуская её вывод и код возврата насквозь. Копия
команды лежит рядом простым текстом.

Фоновая передача не только не мешает — она же убирает задержку: отправитель ценой почти в
секунду работает параллельно, а не до.

Это единственная запись приложения в `~/.claude/settings.json`, и трогается там **только** ключ
`statusLine`. Ключа `hooks` приложение не касается ни на чтение состояния, ни на запись.

### Codex: слияние в общий файл

Плагинов с работающими хуками у Codex нет (см. §7), поэтому его хуки сливаются в
`~/.codex/hooks.json` рядом с чужими. Повторная установка ничего не добавляет: наши записи
сначала снимаются, а потом ставятся — это же делает переустановку после переезда бинарника
перезаписью пути, а не второй записью.

**Наши записи дописываются в конец списка**, и это не стилистика: доверие у Codex позиционное
(§4), поэтому сдвиг чужой записи стоил бы человеку её подтверждения. Свойство закреплено
тестом `testOurEntriesGoAfterSomebodyElsesSoTheirsNeverMoves`.

## 3. Какие события мы просим

### Claude — 13

`SessionStart`, `SessionEnd`, `UserPromptSubmit`, `Stop`, `StopFailure`, `PermissionRequest`,
`PermissionDenied`, `PreToolUse`, `PostToolUseFailure`, `PreCompact`, `PostCompact`,
`SubagentStart`, `SubagentStop`.

### Codex — 11

`SessionStart`, `SessionEnd`, `UserPromptSubmit`, `Stop`, `Interrupt`, `PermissionRequest`,
`PreToolUse`, `PreCompact`, `PostCompact`, `SubagentStart`, `SubagentStop`.

**Просим всё, что агент отдаёт, кроме одного отказа ниже.** Событие, которое агент шлёт, а мы
не просим, — молча потерянный факт: ни строки, ни счётчика, заметить нечем. Обратная ошибка
видна не лучше, но стоит денег — лишний хук оплачивается запуском процесса.

Поэтому список держат два теста, и смотрят они в разные стороны.
`testEveryHookAskedForIsOneTheProtocolUnderstands` ловит лишнее: каждое запрошенное событие
протокол обязан понимать. `testCodexIsAskedForEveryEventCodexOffersAndDeclinesOnlyOnPurpose`
ловит недостающее: список сверяется с каталогом событий агента, записанным там же руками, и
отдельно перечисляет то, что мы не просим намеренно. Каталог руками — потому что это знание о
чужом продукте: тогда расхождение приходит падающим тестом и diff, который надо прочитать и
одобрить. Список отказов нужен, чтобы тест нельзя было починить, снова попросив событие.

Хуки все обязательны: отсутствие любого — неисправность, о которой приложение сообщает.
Необязательных нет, и это решение, а не недоделка — см. следующий раздел.

### Отклонено: `PostToolUse`

**Мы его не просим ни у одного агента.** Единственное, что он делает, — закрывает активность, а
это уже делают две другие вещи:

- **чтение транскрипта** превращает запись `tool_result` в тот же факт. Проверено на 8
  транскриптах, 324 МБ, 16 731 вызов инструмента: без `tool_result` не остался ни один вид,
  включая MCP, `Agent` и `Skill`;
- **конец хода** подметает всякую активность, которая ход не переживает, поэтому вызов без
  сообщённого конца не живёт дольше своего хода. Пережить ход может только сабагент.

То есть хук покупает не факт, а свежесть: строка теряет завершившийся вызов на несколько секунд
раньше. Платит за это запуск процесса на каждый вызов инструмента — 0,78 с на машине, где это
мерилось, то есть вдвое дороже для лёгкого `Read`.

Переключатель рассматривался и отвергнут. Выигрыш маленький, а выключатель, которым никто не
пользуется, — это машинерия, которую надо поддерживать: признак у хука, отдельное состояние
установки, отдельная формулировка в меню. Приложение при этом описывало выбор, которого не
давало сделать. Закреплено тестами `testNeitherAgentIsAskedForPostToolUse` и
`testAToolCallIsClosedByTheEndOfItsTurnWithNoPostToolUse`.

`PostToolUseFailure` мы просим, и это не противоречие: успех бывает на каждом вызове,
падение — редко, поэтому цена почти нулевая. А факт полезен: упавший вызов иначе закроется
только концом хода.

Протокол `PostToolUse` по-прежнему понимает — событие может прийти от установки, сделанной
старой версией, или прописанной руками. **После обновления хуки стоит переустановить один
раз:** запись, которую мы больше не просим, сама не уходит и продолжает платить запуском
процесса. Состояние установки её не показывает — она наша и работает, а переустановка её
снимает.

### Поле `source` у `SessionStart`

Значения `startup` / `resume` / `clear` / `compact` пропускаются редактором. **Список взят из
документации Claude Code и для Codex не проверен** — не путать с утверждением, что Codex шлёт
`SessionStart` на `/clear`; это как раз открытый вопрос (§8).

## 4. Доверие к хукам у Codex

**Codex требует доверия к каждому хуку, и доверие привязано к позиции записи.** Замерено на
0.140 и 0.153.4: `~/.codex/config.toml` держит таблицу `[hooks.state]`, где у каждого хука
лежит `trusted_hash`, а ключ имеет вид `путь:событие:индекс_группы:индекс_хука`. Документация
Codex говорит то же о хуках из плагина: установка плагина не делает их доверенными.

Отсюда два следствия.

Первое: после каждой нашей записи хуки Codex не доверены, пока человек не подтвердит их в
самом Codex. Установка из меню — половина дела, и приложение обязано это сказать: иначе
проверка «события пошли» выглядит провалившейся установкой, хотя записи на месте.

Второе: сдвиг чужой записи стоил бы человеку её доверия. Наши записи снимаются, чужие
остаются дословно — но стоит чужой сдвинуться по индексу, и записанный для этой позиции
`trusted_hash` перестаёт ей принадлежать. Человеку пришлось бы заново подтверждать собственный
хук, которого никто не трогал.

Не происходит потому, что наши записи дописываются в конец: чужая, уже лежащая в файле,
индекс не меняет ни при установке, ни при снятии. Проверка на сохранность содержимого этого не
видит — она сравнивает документ, а не порядок, — поэтому свойство закреплено отдельным тестом
`testOurEntriesGoAfterSomebodyElsesSoTheirsNeverMoves`.

Дописывать доверие самим отвергнуто: подделать хеш доверия значит обойти механизм, который для
этого и существует.

## 5. Состояние установки

### Записывается одно имя, и оно не меняется

В чужой конфигурации стоит `~/Library/Application Support/AgentWatch/AgentWatchSend` — символическая
ссылка, которую приложение направляет на отправителя рядом с собой при каждом запуске. Так путь
в конфигурации не зависит от того, откуда запущено приложение, и переключение между бандлом и
отладочной сборкой ничего не переписывает.

Это не удобство, а условие: Codex хранит `trusted_hash` от содержимого записи, а запись несёт
путь. Путь, меняющийся вместе со сборкой, стоил бы человеку нового подтверждения доверия при
каждом переключении.

**Путь записывается как одно слово для оболочки** — в одинарных кавычках. Оба агента запускают
команду хука через оболочку, а в имени каталога есть пробел: «Application Support». Без кавычек
это две команды, и замерено, чем это кончается — `/bin/sh: /Users/…/Library/Application: No such
file or directory`, код возврата 127. Все хуки падали молча, потому что упавший хук по замыслу
не мешает агенту, и виджет просто перестал слышать сессию. Записи, сделанные без кавычек, при
чтении по-прежнему признаются нашими: иначе переустановка не убрала бы старую запись, а добавила
бы свою рядом, и каждый хук срабатывал бы дважды.

Ссылка обновляется при запуске, а не при установке: тогда она указывает на копию, которая
работает прямо сейчас. Если создать её не удалось, записывается реальный путь отправителя:
мониторинг обязан отказывать в открытую, а имя ссылки, которой нет, запускало бы ничто.

**Сборка без отправителя ссылку не забирает.** Xcode собирает только те продукты, которые
названы в схеме, а `AgentWatchSend` — отдельный продукт пакета. Общая схема репозитория
(`.swiftpm/xcode/xcshareddata/xcschemes/AgentWatch.xcscheme`) называет оба и существует ровно
поэтому; автогенерированная схема собирала одно приложение, и рядом с ним отправителя не было.
Правило нужно и при этом: любая сборка чужой схемой или частичная сборка снова оставит
приложение без отправителя. Поэтому правило «отправитель — файл
рядом со мной» в мире Xcode дало бы ссылку на несуществующий файл и заглушило бы работавшие
хуки. Ссылка остаётся прежней, и отправитель из установленного бандла доставляет событие в
socket — а socket слушает та копия, которая держит замок, кем бы этот отправитель ни был
собран. Отсюда и получается, что отладочная сборка полнофункциональна, ничего не переустанавливая.

Если же ссылки нет и отправителя рядом тоже нет — первый запуск из Xcode на чистой машине, —
записывается отсутствующий путь сборки. Он не работает, но он и есть объяснение; ссылка,
названная рабочей, объяснением не была бы.

### «Устарела» значит «файла нет»

Не «путь не тот, который прописал бы я сейчас». Отправитель только доставляет событие в socket,
и отладочная сборка с установленным бандлом друг другу не мешают. Сравнение с «моим» путём
мигало бы при каждом переключении между сборками и сообщало бы о неисправности там, где всё
работает.

### «Установлено» не означает «работает»

Записи на диске говорят, чего мы просим у агента, а не что он с этим делает. У Codex не делает
ничего, пока хуки не подтверждены (§4) — и со стороны полные записи при молчащем агенте выглядят
точно как агент, которым сегодня не пользовались.

Поэтому состояние учитывает ещё одно, чего в конфигурации нет: **приходило ли от этого агента
хоть одно событие.** Приложение помнит это само, в `agents-heard.json` рядом с журналом. Файл, а
не `UserDefaults`: домен настроек зависит от способа запуска — одно имя внутри бандла, другое под
`swift run`, — и память там сбрасывалась бы при каждом переключении между установленной копией и
отладочной сборкой.

Считается **любое** событие, включая то, которое приложение не смогло разобрать: оно всё равно
дошло до сокета, а это и есть проверяемый факт.

Утверждение при этом узкое, и это главное в нём. «Молчит» говорится только про записи, которые
поставило само приложение (`recordInstall` при установке из меню, `forgetInstall` при снятии).
Про записи, которых оно не ставило, оно молчит: они могли работать месяцами до того, как
приложение начало вести эту память, и объявлять их неисправными на первом же запуске новой версии
значило бы врать. Отсюда три ответа — `arrived`, `nothingSinceInstall`, `unknown`, — и `unheard`
получается только из среднего.

Что видно человеку: строка окна `Installed — 11 hooks, and nothing has arrived from this agent yet`,
а в пустом виджете — `Hooks are installed, but no event has arrived`. Рядом со строкой стоит и
совет, потому что причины у двух агентов разные: Codex ждёт подтверждения доверия, Claude Code не
перечитает уже загруженный плагин без `/reload-plugins`. Обе фразы даёт `toolingHookNextStep`.

### Виджет просит ровно одну вещь

Чтобы хоть один агент мог ему сообщать. Без этого он говорит, что делать, вместо того чтобы
стоять пустым без объяснения. С одной установленной интеграцией он не упоминает остальные
никогда: выбрать только Claude на машине, где есть и Codex, — это решение, а не недонастройка.

## 6. Обращение с чужими файлами

Правило формулируется по содержимому, а не по владельцу: **копия делается перед всякой записью
в то, что писало не приложение.** Копия с отметкой времени и суффиксом при совпадении имён —
перезаписать вчерашнюю копию сегодняшней значит потерять ровно то, что хранится.

Мест три: `~/.codex/hooks.json`, `~/.claude/settings.json` и `original-command.txt`. Последний
лежит в нашем каталоге и потому выглядел нашим, но хранит команду человека и остаётся её
единственной записью — снятие статус-строки читает только его. Каждое место закреплено тестом,
и каждый тест проверен на то, что без вызова копирования он краснеет.

## 7. Отклонено: плагин с хуками у Codex

**Хуков в плагине Codex не существует: функция удалена.** Это ответ самого Codex, а не вывод из
наблюдений — `codex features list` показывает `plugin_hooks` со стадией **`removed`**, тогда как
сам `hooks` стоит `stable true`.

Флаг может однажды сменить стадию, поэтому вот как это перепроверить, целиком: каталог с
`.claude-plugin/marketplace.json`, внутри `plugins/<имя>/` с `.codex-plugin/plugin.json` и
`hooks/hooks.json`, дальше `codex plugin marketplace add <каталог>` и `codex plugin add`. Хук —
отдельный исполняемый файл, а не команда с кавычками и перенаправлением: команду Codex
запускает без оболочки.

Две ловушки, каждая из которых даёт ложный ответ:

- **строки `hook: SessionStart` в выводе Codex ничего не значат** — они печатаются и при
  выключенном плагине, так что это метки событий, а не подтверждение запуска;
- **скрипт надо сначала проверить руками**, иначе «не сработало» может означать «не сработал
  мой же скрипт».

Проверено так на 0.140 и 0.153.4: плагин установлен, `enabled = true`, файл хуков в кэше — ни
одного срабатывания. Принудительное `features.plugin_hooks = true` тоже ничего не включает: имя
флага осталось, возможности за ним нет.

Открытый [issue #16430](https://github.com/openai/codex/issues/16430) «runtime executes only
global hooks.json» описывает ту же вещь со стороны отставшей документации.

Значит общий `~/.codex/hooks.json` — не компромисс, а единственный существующий механизм, и
возвращаться к вопросу незачем, пока `plugin_hooks` не сменит стадию.

## 8. Приём сеансов Codex, и открытый вопрос про `/clear`

Codex Desktop вызывает hook и для внутренней служебной сессии. Она похожа на обычную по
`SessionStart` и `UserPromptSubmit`, но не создаёт тред в `session_index.jsonl`; именно она
давала безымянную дублирующую карточку. Отправитель уже читает этот индекс ради имени, поэтому
тем же одним чтением подтверждает, что сырой `session_id` принадлежит индексированной
пользовательской сессии, прежде чем отправлять событие. Отсутствие `thread_name` отказом не
является: новый пользовательский тред может быть ещё не назван.

**Реакция на `/clear` не требует ничего нового.** Идентификатор сессии при очистке
переиспользуется — на это движок уже опирается, чтобы вернуть закрытую сессию к жизни, — а
`SessionStart`, пришедший в работающую сессию, и есть всё сообщение: сброс, который начало
сессии выполняет всегда, гасит активности и ставит фазу `idle`.

Поэтому вопрос про `/clear` — не про реакцию, а про доставку. Проверено, что мешает не приём:
проверка допуска читает индекс целиком (`codexIndexByteCount = Int.max`), индексированная
сессия проходит её насквозь, и прогон всей цепочки настоящим отправителем даёт в журнале обе
записи — начало работы и очистку. **Остаётся одна невыясненная возможность: Codex на `/clear`
хук не шлёт вовсе.** Решается одной командой в живом сеансе.

## 9. Что обязан делать отправитель

Отправитель — `AgentWatchSend`, лежащий рядом с приложением; хук указывает на него через
постоянную ссылку (см. раздел 5). Он делает только пять вещей:

1. прочитать JSON из stdin;
2. определить источник события;
3. отбросить событие, которое не о самой сессии;
4. отправить payload в Unix socket приложения;
5. быстро завершиться.

Третий пункт — единственное решение, которое больше принять негде, и потому он здесь. Хуки
вызова инструмента, сработавшие **внутри сабагента**, несут `session_id` родителя, поэтому на
той стороне сокета они неотличимы от собственных вызовов сессии. Отличает их путь транскрипта
в payload (`…/subagents/agent-….jsonl`), а путь по проводу не ходит. Замер, из-за которого это
понадобилось: за пять минут работы одного сабагента на строке родителя открылось 48 вызовов
оболочки, и ни один не закрылся — `PostToolUse` для них не приходит, а результат сабагент
пишет в свой файл, который приложение читать не имеет права. Отбрасываются `PreToolUse`,
`PostToolUse`, `PostToolUseFailure` и `PermissionDenied`; `SubagentStart`/`SubagentStop` и
`PermissionRequest` идут дальше. Подробности решения — `docs/architecture.md` §7,
`SubagentToolCall` в коде. Всё остальное отправитель пропускает: судить о смысле события — не
его дело.

Он не анализирует команду, не открывает базу и не запускает модель. Если приложение не работает
или обновляется, отправитель завершается успешно: мониторинг никогда не должен блокировать
агента.

Ограничений по времени два, и они разного назначения. Внутреннее — 100 миллисекунд на
чтение своего входа и столько же на запись в сокет: это то, что не даёт отправителю висеть, и
живёт оно в самом отправителе. Внешнее — таймаут хука в конфигурации, 3 секунды: страховка от
патологии уровня процесса. Страховка должна быть щедрой: на одной секунде она срабатывала при
обычном всплеске нагрузки, теряя событие и показывая пользователю ошибку. В нормальном случае
расширение ничего не стоит, потому что хук завершается по выходу процесса, а не по истечении
таймаута.

Одна часть работы под внутренний дедлайн не попадает — чтение хвоста транскрипта. На локальном
диске это несколько миллисекунд, но при занятом диске единственной границей остаётся таймаут
хука. Это известный предел, а не недосмотр.

**Цена хука — это запуск процесса, а не его работа.** Замерено на машине с корпоративным
агентом безопасности, разрешающим каждый `exec`: `fork` без запуска программы — 0,7 мс,
`/usr/bin/true` — 255 мс. Агент вызывает хук через оболочку, поэтому один хук стоит 0,78 с, из
которых собственная работа отправителя — 5–12 мс; отладочная и release-сборки неразличимы.
Отсюда вывод, обратный ожидаемому: оптимизировать код отправителя бессмысленно, а хуков надо
регистрировать столько, сколько нужно, и не больше.
