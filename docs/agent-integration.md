# Встраивание Agent Watch в агентов

Здесь — чем Claude Code и Codex отличаются для Agent Watch и где каждое отличие живёт в коде.
Чего здесь нет: куда и как приложение пишет хуки и статус-строку —
[agent-install.md](agent-install.md); какие события приходят и что делает отправитель —
[agent-events.md](agent-events.md); как найти живого агента по процессу —
[agent-processes.md](agent-processes.md).

**Почему документы разбиты по темам, а не по агентам.** Почти всё ценное здесь —
сопоставительное. «`Interrupt` есть только у Codex», «доверие требует только Codex», «процент
контекста у Claude берётся из статус-строки, а у Codex из транскрипта» — каждый такой факт
пришлось бы либо задвоить, либо произвольно приписать одному из файлов. Резать по агентам
значит резать поперёк знания.

Общая модель событий, в которую всё это нормализуется, живёт отдельно и намеренно не зависит от
агента — см. [«Единая модель событий»](session-model.md#единая-модель-событий).

## Чем два агента отличаются

Таблица — вход в документы по темам: всё, что в ней стоит, объяснено там.

| | Claude Code | Codex |
|---|---|---|
| куда ставятся хуки | свой каталог-плагин `~/.claude/skills/agent-watch/` | слияние в чужой `~/.codex/hooks.json` |
| плагин, несущий хуки | есть и работает | есть, но хуки в нём не исполняются: `plugin_hooks` в стадии `removed` |
| доверие к хукам | не требуется | **требуется**, по хешу содержимого и позиции записи |
| когда правка доходит | после `/reload-plugins` или новой сессии | со следующего сеанса |
| событий просим | 15 | 11 |
| прерванный ход | хука нет — только чтение транскрипта, до 10 с | `Interrupt`, сразу |
| процент контекста | только из пейлоада статус-строки | приходит записью транскрипта |
| где живёт сессия | терминал, у фоновой — свой pty агента ([«Почему живой агент находится только у Claude»](agent-processes.md#почему-живой-агент-находится-только-у-claude)), у десктопной — Claude.app ([«Десктопные приложения»](agent-processes.md#десктопные-приложения)) | ChatGPT.app (`com.openai.codex`, [«Десктопные приложения»](agent-processes.md#десктопные-приложения)), делит `~/.codex/` с CLI |
| служебные сеансы | нет | есть, отсекаются по `session_index.jsonl` |
| как узнаётся хост сессии | процесс-предок хука, наблюдение за его выходом | процесс плюс бандл приложения |
| номер процесса в событии | приходит с каждым хуком | не приходит вовсе (замер: Codex, версия не записана) |
| сессия по живому процессу | находится: один процесс — одна сессия | не находится, см. [«Почему живой агент находится только у Claude»](agent-processes.md#почему-живой-агент-находится-только-у-claude) |

Одна асимметрия стоит того, чтобы назвать её отдельно: `Interrupt` — единственное место, где
Codex богаче. У Claude прерванный ход не порождает ни одного хука, и приложение узнаёт о нём
только чтением транскрипта по тишине; ради этого случая расписание чтения и держит проверку в
покое.

## Где это живёт в коде

Набор задан данными: `ToolingHooks.hooks(for:)` и `ToolingIntegrations.kinds(for:)` — вся
таблица. Первая говорит, какие события просить у агента, вторая — что вообще можно в него
поставить (у Claude Code это хуки и статус-строка, у Codex только хуки). Третий агент — две
записи в одном файле `AgentWatchCore/ToolingIntegration.swift`.

Окно `Tooling` — проекция этой таблицы, а не список, написанный руками: `ToolingReport.sections`
обходит `AgentSource.allCases`, а каждая строка несёт в себе интеграцию, которой управляет.
Закреплено тестом `testTheWindowIsAProjectionOfTheAgentsAndTheirIntegrations`: без него агент,
добавленный в таблицу, оказался бы устанавливаемым и невидимым.

У установщика по одной точке входа на операцию — `hookState(for:)`, `installHooks(for:…)`,
`removeHooks(for:)`. Внутри каждой switch по агенту, и это правильно: механизмы действительно
разные — свой каталог у Claude Code против слияния в чужой файл у Codex. Смысл в том, что
switch случается один раз в одном месте, а не у каждого вызывающего.

**Правила агента — по типу на агента в каждом слое, а не один общий описатель.** Один тип на
агента невозможен: код агента работает в двух программах — в отправителе, которого агент
запускает на каждый хук, и в самом приложении, — и такой тип пришлось бы протянуть через все цели
сборки. Но у слоя может быть свой: протокол, чьи ответы — общие понятия модели (номер процесса,
`SessionClientKind`, `DiscoveredAgentProcess`, событие), и по реализации на агента. Агент, который
чего-то сообщить не может, отвечает ничем, а не пропуском вопроса: асимметрия из таблицы [«Чем два агента отличаются»](#чем-два-агента-отличаются) видна в
одном месте, а не как `if source == .claude` у каждого вызывающего. Выбор реализации — один
switch на слой.

Переведён один слой, `AgentWatchLookup`. `AgentProcessRules` — с `ClaudeProcessRules` и
`CodexProcessRules` — отвечает, какой процесс агента, где живёт сессия, какую сессию продолжает
копия и находятся ли сессии по процессам вообще; им пользуются и отправитель, и сканер, поэтому
ответить по-разному они не могут. Остальные слои переводятся, когда их трогают; какие именно —
в [плане](implementation-plan.md#технический-долг). Пока слой не переведён, его различия стоят по одному switch в том месте,
которое про это знает, и новый вариант `AgentSource` компилятор покажет в каждом из них.
