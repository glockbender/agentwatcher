# Как наблюдать Skip асинхронного вопроса Codex

> **Архив.** Исследование закрыто 2026-11-25. Здесь результаты проверок журналов,
> телеметрии и обработчика Skip; готовой интеграции наблюдения здесь нет.
> Текст сохраняет факты на указанных версиях и больше не обновляется. Ограничение для
> пользователя — в [TROUBLESHOOTING.md](../../TROUBLESHOOTING.md#the-waiting-lamp-stays-on-after-skip-in-codex),
> условие возврата к работе — в [плане](../implementation-plan.md#наблюдение-skip-в-codex).

## Вывод

Установленные файлы Codex можно оставить неизменными и увидеть ручной Skip через временный
отладчик: в обработчике ещё есть точные идентификаторы чата и вопроса. Это подтвердил живой
тест. Однако штатного внешнего источника с таким событием в проверенных каналах не найдено.
Подключение отладчика к интерфейсу остаётся способом исследования, а автоматическое снятие
ожидания в Agent Watch по этому способу не реализовано.

Результаты и запрос поддерживаемого события опубликованы в
[openai/codex#44648, наш комментарий](https://github.com/openai/codex/issues/44648#issuecomment-7149227298).
Он дополняет [запрос наблюдения за вопросами настольного клиента](https://github.com/openai/codex/issues/44648#issuecomment-6383986516).
Сам номер #44648 относится к вопросам CLI; комментарий явно уточняет область запроса.

## Почему перехвата аналитики недостаточно

В исследованной сборке обработчик `t62K.Hu(e, t)` передаёт в `CodexRequestInputDismissed`:

- `kind: "user_input_async"`;
- `dismissalReason: CODEX_REQUEST_INPUT_DISMISSAL_REASON_QUESTION_SKIPPED`;
- `questionCount`;
- `hasUnsubmittedResponse`.

Обогащение события и форматы отправки Segment и Statsig не добавляют идентификатор чата
или вопроса. `sessionId` в аналитике обозначает сессию приложения, а не чат Codex.
Выполнение тех же функций с двумя вымышленными чатами дало одинаковые полезные данные
события: выбрать нужное ожидание по ним нельзя.

Для сверки кода исследованный ресурс: `webview/assets/async/49792.ab5b643c25.js`, SHA-256:
`03952fe51b17e007970cfac117234ad8cad81a50c00310d56dd3c78fd11e8a1c`.
Имя модуля и аргументов — детали этой сборки, а не стабильный интерфейс.

## Что доказал живой Skip

Отдельный экземпляр запущен с временными каталогами данных приложения и `CODEX_HOME`.
Установленный комплект приложения, `BUILD_FLAVOR` и защитные флаги не изменялись.
Временный отладчик слушал только `127.0.0.1:19333`; его принадлежность тестовому экземпляру
проверена. Пользователь сам открыл DevTools через Chrome: в обычном меню этой сборки
пункта DevTools не было.

После вычисления локальной переменной `n` в `t62K.Hu`, перед отправкой аналитики,
пользователь поставил условную точку останова. Условие записывало только время,
`t.hostId`, `t.threadId` и `t.itemId` в массив `globalThis.__agentWatchSkipProbe`
и возвращало `false`, чтобы выполнение продолжалось.

При ручном Skip в `2026-11-25T00:55:47.558Z` получены:

```json
{
  "hostId": "local",
  "threadId": "<идентификатор тестового чата>",
  "questionItemId": "[\"request_user_input_async\",\"call_...\",0]"
}
```

Идентификаторы в примере заменены. В исходной проверке `threadId` совпал с метаданными
журнала, а вызов и индекс — с записью открытия вопроса за несколько секунд до Skip.
Соответствующего ответа в журнале не было. Это доказывает доступность точной привязки
в момент вызова обработчика, но не наличие поддерживаемого внешнего события после
успешного изменения состояния вопроса.

Ранние опыты содержали окно без Skip и самопроизвольно закрывшийся запрос. Они не считаются
подтверждением ручного Skip; положительный результат выше относится к отдельному нажатию,
которое пользователь явно подтвердил.

Отладчик даёт возможность читать и выполнять код в тестовом приложении. Для обычной работы
этот режим не предназначен: после опыта нужно убрать точку останова и закрыть тестовый
экземпляр. Данные опыта не нужны для запуска Agent Watch; работа продукта от них не зависит.

## Какие обходы не дают точного ответа

Новая строка журнала, возобновление работы после паузы, конец хода, таймаут и скрытая панель
не доказывают закрытие конкретного вопроса. Асинхронный вопрос может оставаться открытым,
пока агент работает. Снятие ожидания по такой эвристике может погасить настоящий запрос
пользователю, в том числе другой вопрос того же вызова.

Отладчик решает задачу наблюдения в опыте без правки установленного приложения, но требует
особого запуска и зависит от внутреннего кода интерфейса. Поэтому результат исследования
не означает, что найден пригодный для штатной интеграции способ.

## Что запросили у Codex

Поддерживаемое событие только для чтения: через хук, локальную подписку или историю сессии.
Нужны идентификатор чата, исходный вызов и индекс вопроса либо равнозначный стабильный ID,
подтверждённый переход с отдельной причиной `skipped`/`dismissed` и порядок событий для
восстановления после переподключения. Тексты вопросов и ответов не нужны.
Пропуск Q1 должен снимать только Q1, сохраняя Q0 и остальные вопросы и разрешения.

В опубликованном комментарии также указаны
[#46169](https://github.com/openai/codex/issues/46169) — запрос событий разрешения,
пропуска и очистки для клиентов app-server — и
[#57130](https://github.com/openai/codex/issues/57130) — похожий симптом оставшегося
`Input required` после Skip. Общая причина этих сообщений не доказана; статус связанных
задач сам по себе не подтверждает исправление внешнего наблюдения.
