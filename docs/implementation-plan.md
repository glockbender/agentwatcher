# План реализации Agent Watch

Здесь этапы развития, состояние каждого, критерии готовности и решения, которые ещё не приняты.
Чего здесь нет: что осталось до 1.0 и ближайший релиз — это [план до 1.0](release-plan.md);
как устроено то, что уже сделано, — остальные документы в `docs/`; что и когда сделано — история
git.

**Статус:** этап 1 — функциональная alpha и dogfooding; последний релиз — 0.4.0 (2026-10-10), с
changelog и окном обновления, где видно, что изменилось.
**Дата актуализации:** 2026-10-10

## Цель

Создать лёгкое самодостаточное macOS-приложение, которое показывает состояния параллельных Claude
Code и Codex-сессий, а затем постепенно получает диагностику зависаний, удобную настройку и
локальные LLM-возможности.

План намеренно разбит на вертикальные стадии. Каждая должна дать проверяемый пользовательский
результат и новую обратную связь, а не только подготовить инфраструктуру для следующей.

## Зафиксированные решения

- Первый релиз — только Apple Silicon (ARM64), macOS 14+. Intel и universal-сборка не планируются.
- Runtime и единственный источник состояния находятся в `AgentWatch.app`.
- Отдельный daemon не создаётся.
- Приложение строится AppKit-first и продолжает работать после закрытия окна настроек.
- Claude и Codex передают события напрямую приложению через hooks.
- Общей упаковки на две экосистемы нет: у Claude Code это каталог-плагин, который приложение
  создаёт целиком, у Codex — слияние в его собственный файл хуков. Почему одного механизма не
  получилось — [agent-integration.md](agent-install.md#отклонено-плагин-с-хуками-у-codex).
- Установку, обновление и проверку интеграций выполняет само приложение; отдельного инструмента
  установки нет.
- Файлы состояния — внутренняя деталь приложения; внешние клиенты, когда появятся, пойдут через
  версионированный локальный API.
- Базовые состояния вычисляются детерминированно. LLM не участвует в определении фактов.
- Watchdog сообщает о потенциальном зависании и объясняет причины, но не выдаёт эвристику за
  доказанный факт.
- Данные и аналитика локальны по умолчанию.

## Этап 1. AppKit MVP и dogfooding

**Цель:** получить полезный виджет с достоверными состояниями сессий без диагностики зависаний.

### Dogfooding

- использовать приложение самим в реальных параллельных задачах;
- вести короткий список неверных и непонятных состояний;
- записывать ситуации, когда всё равно пришлось вручную открывать сессию;
- затем дать debug-сборку нескольким коллегам;
- собирать только осознанно отправленный feedback, без фоновой отправки transcript или команд.

### Критерии готовности

- [x] одновременно отображаются Claude и Codex-сессии;
- [x] режим планирования визуально отличается от исполнения;
- [x] основной агент, ожидающий дочернюю работу, не выглядит как безымянное состояние «работает»;
- [x] строка показывает виды текущей работы счётчиками
  ([ADR-0011](adr/0011-the-row-is-a-template-with-one-gap.md));
- [x] клик по строке как минимум активирует правильное host application;
- [x] точный переход используется только тогда, когда окно и вкладку можно назвать достоверно;
- [x] карточка говорит, когда клик сделает не то, что обычно; неверная вкладка не выбирается
  эвристически;
- [x] переходы фаз и жизненный цикл параллельных активностей покрыты тестами;
- [x] закрытие окна не останавливает мониторинг;
- [x] отключённый Agent Watch не замедляет и не ломает агента;
- [x] перезапуск возвращает сессии, за которые ещё есть кому поручиться, и не возвращает остальные;
- [ ] idle CPU, память и wakeups измерены против бюджетов — бюджетов пока нет (открытые решения);
- [ ] feedback достаточен для уточнения этапов 4 и 5.

## Этап 1.5. Session host: закрытие терминала и фокус

**Цель:** связать сессию с фактическим процессом агента без launcher'а и использовать эту связь для
двух действий: достоверно показать завершение сессии и поднять окно host-приложения кликом по
строке.

### Критерии готовности

- [x] завершение процесса агента переводит сессию в `session closed` не позднее чем через 10 секунд;
- [x] клик по строке активирует корректное host application или карточка честно говорит, что
  поднимать нечего;
- [x] завершение процесса не интерпретируется как нормальный `Stop` turn;
- [x] нет launcher'а и PTY proxy; обход процессов идёт, только пока есть живые строки;
- [x] process mapping и exit transitions покрыты детерминированными тестами.

Границы, принятые сознательно:

- закрытая вкладка терминала JetBrains оставляет агента живым, и события у этого нет: строка
  получает фазу `terminal closed` на ближайшем обходе, пробуждении, открытии меню или клике, а не за
  10 секунд ([ADR-0013](adr/0013-a-click-ends-an-agent-its-closed-terminal-left-behind.md));
- у Codex Desktop нет наблюдения за процессом каждой сессии: его runtime общий для нескольких
  задач, поэтому закрывает все его сессии только выход самого приложения.

## Этап 2. Штатная установка хуков из приложения

**Цель:** заменить временную debug-конфигурацию hooks на штатную и обратимую установку. Как она
устроена у каждого агента — [agent-integration.md](agent-integration.md).

### Критерии готовности

- [x] установка не требует ручной правки settings-файлов;
- [x] тестовое событие появляется в Agent Watch;
- [x] выключенное приложение не влияет на работу агента;
- [x] обновление не создаёт дублирующиеся hooks;
- [x] удаление полностью прекращает доставку событий и не трогает чужие записи.

## Этап 3. Установка, обновление и первый запуск

**Цель:** довести путь от скачанного пакета до работающего мониторинга без ручной сборки
компонентов. Как устроены релиз и самообновление — [distribution.md](distribution.md).

### Критерии готовности

- [ ] новая машина проходит путь от скачанного пакета до работающего HUD без ручного редактирования
  settings-файлов и без `xattr`;
- [x] повторная установка интеграции идемпотентна (повторный запуск ничего не меняет);
- [ ] обновление сохраняет настройки и историю — проверить в релизной матрице;
- [x] отказ от обновления не мешает работе текущей версии;
- [ ] новый агентский инструмент, появившийся после первой установки, обнаруживается и предлагается
  к подключению;
- [ ] несовместимые версии диагностируются понятным сообщением;
- [ ] удаление не затрагивает пользовательские данные без отдельного выбора;
- [ ] когда запись в файл агента не удалась (нет прав, каталог только для чтения, шаг доверия у
  Codex), приложение показывает, что вставить руками, а не только «не получилось».

## Этап 4. Проверка потенциальных зависаний

**Цель:** отличать просто долгую работу от операций, которые с высокой вероятностью перестали
продвигаться.

### Сначала — проектирование на реальных данных

- собрать из dogfooding типовые длительные и реально зависшие операции;
- определить доступность PID/process-tree для Claude и Codex;
- проверить стоимость CPU, I/O и FSEvents sampling;
- определить объяснимые сигналы и мягкие пороги;
- разделить foreground tool calls и фоновые процессы;
- определить поведение после sleep/wake.

### Реализация

- возраст незакрытой shell-операции;
- адаптивный sampling только активных операций;
- process existence и CPU-time delta;
- файловая активность через FSEvents;
- несколько измерений перед предупреждением;
- объяснимый `stuck score`;
- действия `snooze` и «ожидаемо долгая команда»;
- локальные baseline по типам команд после накопления истории.

Не входят в первую версию: чтение всего stdout, универсальный PTY proxy, автоматическое завершение
процесса, точный контроль любого процесса, запущенного через `&`, LLM как единственный детектор.

### Критерии готовности

- предупреждение всегда содержит наблюдаемые причины;
- обычные долгие сборки не создают постоянный шум;
- ожидаемое предупреждение можно быстро подавить;
- sleep не увеличивает ошибочно длительность работы;
- overhead watchdog измерен отдельно от idle-режима;
- эвристики покрыты воспроизводимыми сценариями и тестами.

## Этап 5. Полноценный config и management UI

**Цель:** сделать настройку понятной без редактирования файлов и знания внутренней архитектуры.

Окно настроек уже есть: все настройки живут в одном окне
([ADR-0016](adr/0016-every-setting-lives-in-one-window.md)). Осталось:

- запуск при входе;
- настройки этапов, которых ещё нет: предупреждения и snooze watchdog, модели и лимит памяти,
  срок хранения статистики.

Принципы: ясность уровня Handy, а не его внешний вид; показывать состояние интеграции и следующее
действие; технические параметры — в стороне от основных; последствия удаления данных или модели
видны до подтверждения; работоспособные умолчания без обязательной настройки.

### Критерии готовности

- [x] базовая настройка выполняется полностью через UI;
- [x] состояние интеграции диагностируется без чтения логов;
- [ ] экран интеграций показывает доступный уровень навигации для Codex Desktop, а не только для IDE;
- [ ] HUD остаётся компактным;
- [ ] окно не держит локальную модель в памяти после закрытия.

## Этап 6. Ollama и согласованные LLM-функции

**Цель:** добавить локальную интеллектуальную обработку только для сценариев, доказавших полезность.

### Обязательный product gate

Перед реализацией отдельно выбрать функции из кандидатов:

- объяснение подозрительного зависания;
- summary сессии;
- автоматическое короткое имя сессии;
- классификация shell-команд;
- группировка повторяющихся проблем;
- приоритизация сессий, требующих внимания.

Для каждой функции нужны примеры входа, ожидаемый результат, latency budget и способ понять, что она
действительно помогает.

### Технический scope после согласования

- provider interface для local inference, Ollama как первый provider;
- каталог рекомендованных моделей и экраны Downloaded/Available в стиле Handy;
- профили «минимум ресурсов», «сбалансированный», «лучший анализ»;
- lazy loading и выгрузка после idle timeout;
- ограничение контекста и редактирование секретов;
- fallback на полностью детерминированное поведение.

### Критерии готовности

- приложение полезно и без модели;
- модель никогда не определяет фактическое lifecycle-состояние;
- idle-приложение не держит модель загруженной;
- до скачивания видны размер, потребление памяти и назначение;
- ошибка Ollama или inference не ломает мониторинг;
- функции проверены на заранее подготовленных примерах.

## Этап 7. Локальная статистика

**Цель:** дать локальную аналитику по накопленному журналу сессий. Журнала пока нет: приложение
помнит сессии только для восстановления после перезапуска.

### Работы

- журнал сессий и версионированный read API приложения;
- агрегация по источнику, проекту и периоду;
- отдельно считать `attention wait` (агент явно ждёт разрешения или ввода) и `review delay` (ход
  закончен, а человек к результату ещё не вернулся);
- показывать ошибки и suspected-stuck incidents;
- определить retention и экспорт.

### Критерии готовности

- метрики имеют однозначные определения;
- агрегаты можно проверить на небольшом журнале вручную;
- внешние читатели идут через версионированный API, а не через файлы приложения;
- данные остаются локальными, пока обратное не выбрано отдельно.

## Сквозные требования

- **Производительность.** Budgets для idle CPU, resident memory без модели, wakeups, времени hook
  sender, задержки HUD и overhead watchdog получить замером на целевом Mac, а не угадать.
- **Приватность.** Не хранить prompts, ответы и stdout по умолчанию; редактировать чувствительные
  аргументы до записи; не добавлять централизованную телеметрию без отдельного решения.
- **Совместимость.** Версия события есть в каждом запросе; приложение принимает предыдущую
  совместимую версию отправителя; local API, когда появится, версионируется.
- **Качество.** State machine проверяется табличными unit-тестами, адаптеры — на обезличенных
  payload fixtures; каждая найденная ошибка перехода получает regression fixture.

## Технический долг

**Правила агента по слоям.** Принцип — тип правил на агента в каждом слое
([agent-integration.md](agent-integration.md#где-это-живёт-в-коде)). Переведён слой
`AgentWatchLookup`. Остальные переводятся, когда их трогают:

- чтение транскрипта и имени сессии — `TranscriptLocator`, `TranscriptReader`,
  `SessionDescriptionResolver` и его ветка Codex в отправителе;
- запись реестра Claude: ядро состояний принимает `ClaudeSessionStatus` и проверяет
  `source == .claude` (`SessionStateEngine.apply`), а должно принимать общий факт «на диалог
  ответили»;
- установка хуков и значок.

  `event-debug.log` на нажатие и отпускание в строке.
- **Карточка строки при спрятанном виджете.** После выбора сессии в меню над терминалом появилась
  карточка строки (`SessionHoverCard`) другой сессии, хотя виджет был спрятан, а показывает её
  только `HUDPanelController` (замер: macOS 15.7.7). При повторе дубля не появилась. Покажет строка
  в том же журнале на показ и скрытие карточки, с сессией.

## Открытые решения

Каждое — с тем, что его решит.

- **Окончательный bundle identifier** (сейчас `com.glockbender.agentwatch` и у приложения, и у
  плагина). Блокирует первую загрузку плагина: после публикации идентификатор плагина не меняется
  ([план до 1.0](release-plan.md#1-отправить-текущий-плагин-на-первое-ревью-marketplace)).
- **Численные performance budgets.** Решит замер на целевом Mac.
- **Пороги и профили команд watchdog.** Решат данные dogfooding (этап 4).
- **Набор LLM-функций.** Решит product gate этапа 6.
- **Нужен ли централизованный сбор агрегированной статистики.** Решит отдельное продуктовое решение;
  по умолчанию — нет.
- **Статус-строка в других папках Claude.** Сейчас она подключается только в
  `~/.claude/settings.json`, и у сессии из другой папки нет процента контекста
  ([ADR-0022](adr/0022-a-person-names-the-agents-other-folders.md)). Решит просьба человека, которому
  этого не хватает.
- **Подтверждение хуков другой папки в самом Codex.** Что Codex читает только `$CODEX_HOME/hooks.json`,
  пропускает неподтверждённые хуки и запускает хуки, которым проверка не мешает, замерено; что
  подтверждение через его запрос сохраняется для этой папки и работает, — нет
  ([«Другие папки агента»](agent-install.md#другие-папки-агента)). Решит один интерактивный запуск
  Codex с другой папкой, в котором человек подтвердит хуки.
