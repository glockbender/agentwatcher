# Защита Git в Agent Watch

Здесь описаны установка обработчиков Claude и Codex, правила веток, типы веток и проверка обновления
на macOS.
Чего здесь нет: подключение наблюдения за сессиями описано в [Tooling](agent-install.md).

## Подключение и переход с Mothership

1. Поместите сборку с защитой Git в постоянное место, например `/Applications/AgentWatch.app`.
2. В `Settings… → Git Protection → Protect Git commands` выберите клиент и профиль. Нажмите
   `Install Git Hook`. Повторите для каждого профиля, в котором нужна защита.
3. В настольном Codex откройте `Settings → Hooks` и нажмите `Trust` у обработчика `PreToolUse`
   из Agent Watch. В терминальном Codex та же настройка доступна через `/hooks`.
   Откройте новый чат в каждом клиенте. Для проверки используйте локальный учебный репозиторий
   и отмените запрос удаления ветки.
4. Если раньше защиту предоставлял Mothership, обновите его до версии без обработчика Git
   после подключения Agent Watch. Затем откройте новые чаты. Остальные функции Mothership
   обновляются обычным способом.

Claude хранит команду в `settings.json` своего профиля, Codex — в `hooks.json`. Команда указывает
на файл внутри установленного приложения. При замене приложения по тому же пути следующий
вызов запускает новую версию. Проект хранит правила в своей конфигурации Git. Обычное обновление
сохраняет и команду, и правила. Если вы перенесли само приложение, восстановите привязку через
`Repair Git Hook` и проверьте доверие в Codex. Для отключения выберите профиль и нажмите
`Remove Git Hook…`. Пока зарегистрированный обработчик недоступен по указанному пути,
клиент получает отказ с предложением восстановить привязку.

Обработчик проверяет команду оболочки перед её запуском. Для рискованной отправки он возвращает
клиенту причину отказа и команду для однократного запуска `AgentWatchGit push`. Установленное
приложение проверяет команду через `AgentWatchGit hook` на Rust. Python по-прежнему нужен
сценариям сборки и сквозной проверки, которые его вызывают.
Исполнитель на Rust сам проверяет репозиторий и назначение, показывает окно macOS и завершает
работу после решения пользователя. Сервер MCP и запущенное окно настроек для этого не нужны.

## Правило для одного проекта

В настройках откройте `Git Protection`, выберите любую рабочую копию репозитория, введите точное
имя ветки и нажмите `Preview Confirmation`. Для удаления обычной ветки на сервере требуется одно
подтверждение. Для `main`, `master`, основной ветки сервера и ветки из списка защиты потребуется
также ввести имя репозитория. Если основная ветка сервера неизвестна, пример объясняет это условие.
Её определяет исполнитель при обращении к выбранному серверу. Если сервер не сообщает основную
ветку, исполнитель останавливает удаление ветки, для которой ещё не действует правило защиты.
Так проверяется ветка без типа; тип ветки меняет уровень в пределах пола, см. [«Типы веток»](#типы-веток).

`Require Repository Name` добавляет ветку в локальный список `mothership.protectedBranch`.
Связанные рабочие копии используют этот же список. Снятие правила запрашивает подтверждение и
удаляет только точное значение из основного файла настроек репозитория. Правило из подключённого
файла Git продолжает действовать. Предварительный просмотр и изменение настроек работают без
сетевого соединения. Для защиты команд нужен установленный обработчик Git.

На Mac `AgentWatchGit` показывает отдельное окно Agent Watch. В нём указаны операция, репозиторий и
имя ветки. При отказе, закрытии окна или истечении времени операция останавливается. Агент
не может подтвердить её за человека.

## Типы веток

В `Settings… → Git Protection → Branch types` задаётся таблица типов, одна на все репозитории.
Тип — это имя, шаблоны имени ветки и уровень проверки. Уровень действует на принудительную отправку
(force push) и на удаление ветки на сервере. Остальные отправки проверяются как раньше.

| Уровень в настройках | В файле | Что происходит |
|---|---|---|
| `No Window` | `none` | Окна нет: обычная команда `git push` агента проходит. |
| `Click` | `click` | Одно окно; его кнопка выполняет операцию. |
| `Click + Name` | `name` | Подтверждение, затем ввод имени репозитория. |
| `Forbid` | `forbid` | Отказ без окна. Команду запускает человек в терминале. |

Тип выбирается по первому совпавшему шаблону, сверху вниз. Порядок меняют стрелки в строке типа.
`*` совпадает с любыми символами, включая `/`: `release/*` подходит и для `release/2026/q1`. `?` —
один любой символ. Остальные символы сравниваются точно, с учётом регистра. Шаблоны разделяются
пробелом: в имени ветки пробела не бывает, а запятая бывает.

Ветка без типа проверяется как раньше: удаление — одно подтверждение, принудительная отправка —
подтверждение и имя репозитория. Пока таблица пуста, ничего не меняется.

**Пол.** `main`, `master`, основная ветка сервера, ветки из `mothership.protectedBranch` и метки
всегда требуют не меньше `Click + Name`. Тип может только поднять их до `Forbid`. Правило
`Require Repository Name` тоже только поднимает уровень. Агент работает от того же пользователя и
может изменить любой файл настроек, поэтому гарантию даёт только пол
([ADR-0024](adr/0024-a-branch-type-chooses-the-check-above-a-floor.md)).

### Файл таблицы

Приложение записывает таблицу в `~/Library/Application Support/AgentWatch/git-branch-types.json`.
`AgentWatchGit` читает её при каждой проверке, через `HOME` того процесса, который его запустил:

```json
{
  "types" : [
    { "level" : "none", "name" : "Agent drafts", "patterns" : [ "agent/*", "tmp/*" ] }
  ],
  "version" : 1
}
```

Если файла нет, он не читается, у него другая версия или неизвестный уровень, `AgentWatchGit`
считает, что типов нет, и проверяет ветки как раньше. Страница настроек показывает такую ошибку.
Отладочная копия приложения с `AGENT_WATCH_SUPPORT_DIR` пишет таблицу в свою папку, а
`AgentWatchGit` ищет её только по `HOME`.

### Как уровень применяют обработчик и исполнитель

Исполнитель `AgentWatchGit push` знает точное назначение и применяет уровень всегда. При `none` он
выполняет операцию без окна, при `forbid` отказывает без окна и возвращает команду для терминала.
Если таблица изменилась, пока окно было открыто, и уровень вырос, операция останавливается.

Обработчик пропускает принудительную отправку или удаление при `none` только тогда, когда то, что
он прочитал, совпадает с тем, что увидит `git push`:

- **Команда одна.** Во вводе нет ничего, кроме `git push`: ни `cd`, ни `|`, ни `;`, ни присвоения
  переменной перед `git`, ни `git -C` или `git -c`. Иначе соседняя команда может переключить
  `HEAD`, создать ссылку или сменить папку между проверкой и отправкой.
- **Текст буквальный.** В команде только латиница, цифры, пробел и `-_./:+=,@`: без `$`,
  кавычек, скобок, перенаправлений и второй строки. Парсер оболочки не заглядывает в каждую
  подстановку (тело heredoc, `${x:-$(…)}`), а подстановка выполняется до `git`.
- **Флаги простые.** Разрешены только `-f`, `--force`, `--force-with-lease`, `--force-if-includes`,
  `-d`, `--delete`, `-u`, `-q`, `-v`, `--no-verify`, `--progress` и `--porcelain`. `--mirror`,
  `--tags`, `--all`, `--prune`, `--recurse-submodules`, `--receive-pack` и любой неизвестный флаг
  оставляют проверку.
- **Назначение — точно ветка.** `<dst>` после двоеточия (и в `name:name` тоже) и имя для удаления
  должны быть полными:
  `refs/heads/…`. Короткое имя Git ищет среди ссылок сервера, и `v1`, `tags/v1` или `heads/main`
  могут оказаться меткой или другой веткой. Локальное имя без двоеточия должно разрешаться ровно в
  `refs/heads/<имя>` (`git rev-parse --symbolic-full-name`); `HEAD` — в текущую ветку, `@` не
  принимается. На сервере назначению не должна соответствовать никакая другая ссылка: Git
  сопоставляет и полное имя по окончанию, и `refs/tags/refs/heads/x` забрал бы отправку.
- **Подмодули не отправляются.** При `submodule.recurse` или `push.recurseSubmodules` в
  конфигурации окно остаётся: подмодуль уходит на сервер, который проверка не спрашивает.
- **Пол проверен у сервера.** Основную ветку обработчик спрашивает у сервера так же, как
  исполнитель, и читает `mothership.protectedBranch` тем же запросом. Сервер должен быть описан в
  конфигурации Git (`remote.<имя>.url`): сервер из старых файлов `.git/branches` и `.git/remotes`
  приносит свои правила отправки, которых проверка не видит. Это правило действует и для
  `AgentWatchGit push`.

Во всех остальных случаях обработчик отказывает с отсылкой к `AgentWatchGit push`. Агент делает
лишний шаг, а исполнитель с точным назначением выполняет `none` без окна. При `forbid` обработчик
отказывает и не предлагает `AgentWatchGit`, если назначение доказано; короткое имя он отправляет
к исполнителю, и тот отказывает сам. Прочие риски команды (`--all`, `--prune`, шаблоны `*`, `-c` в
команде, отправка по настройкам Git) проверяются как раньше при любом уровне.

Обработчик проверяет команды, которые он узнаёт, и не заменяет песочницу: отправку через псевдоним
Git, `=git` в zsh или `xcrun git` он не распознаёт, как и до типов веток. Путь без окна не добавляет
нового способа задеть пол, но против агента, который нарочно обходит проверку, гарантия — только
исполнитель и сервер Git
([ADR-0024](adr/0024-a-branch-type-chooses-the-check-above-a-floor.md)).

Обработчик видит окружение агента, а не оболочки, в которой выполнится команда. Если оболочка
получает `GIT_DIR` или `GIT_CONFIG_PARAMETERS` из файлов запуска, обработчик этого не знает. Так
было и до типов веток; правка файлов запуска — тот же уровень доступа, что правка таблицы.

## Ручная проверка подтверждений

```sh
task test-git-windows
```

Один сценарий на Rust создаёт временный репозиторий и локальное назначение. Для
`feature/example` нажмите «Отменить всю операцию». Для основной ветки `trunk` разрешите
первый шаг и отмените на втором, когда появится поле имени репозитория. Проверка
сверяет место отмены и исходные ссылки после каждого запроса. Учебный сервер
дополнительно запрещает удаление. По умолчанию открывается окно из текущих исходников.
Для проверки установленной сборки укажите путь к её исполнителю.

```sh
AGENT_WATCH_TEST_GIT_BIN=/Applications/AgentWatch.app/Contents/MacOS/AgentWatchGit task test-git-windows
```

Тот же сценарий входит в `task test-native-git`. В автоматическом режиме ответы
на подтверждения задаёт тест, а Git и временные репозитории настоящие.
Команда `task test-git-window-cancellation` открывает реальные окна и проверяет, что они
закрываются при разрыве соединения с вызывающим процессом.

## Проверка обновления и закрытия чата

Сценарии обновления и закрытия чата написаны на Rust (`native/git-protection-e2e`) и работают
только в одноразовой виртуальной macOS с открытым графическим сеансом: окна подтверждения
открываются на её экране. Вне виртуальной машины сценарий отказывается запускаться. Каждый
клиент получает временный профиль, локальный ответ модели и собственный репозиторий
с локальным сервером Git. Код подтверждения и сами клиенты настоящие.

В гостевой системе нужны Git, инструменты командной строки Xcode и оба клиента. Пути к клиентам
можно указать в `CLAUDE_BIN` и `CODEX_BIN`. Для Codex из настольного приложения сохраните на диске
гостя весь подписанный комплект `CodexCLI.app` и укажите путь к исполняемому файлу внутри.
Комплекты приложений передавайте в гостя архивом (`ditto -c -k --keepParent`): общая папка Tart
ломает символические ссылки внутри `Sparkle.framework`, и `codesign` отвергает такую копию.
Задачи `task` собирают сценарий через Rust 1.98.1 и файл `Cargo.lock`. Без Rust в госте соберите
на хосте исполняемый файл `agent-watch-git-e2e` и запустите его с теми же аргументами.

Для проверки обновления передайте тесту собранное приложение. Временные профили получают
обработчики один раз. Тест включает исходное доверие через API Codex, заменяет подписанный
комплект приложения на диске и проверяет реальные окна обоих клиентов на локальном репозитории.
Затем он временно убирает комплект с места установки: оба клиента должны получить отказ
зарегистрированного обработчика, а запрос не должен дойти до учебного сервера. После возврата
комплекта оба клиента снова получают окно подтверждения. После каждого запроса тест сверяет
ссылки сервера, а после каждого этапа с окнами — ещё доверие Codex, конфигурацию и правила. В `AGENT_WATCH_PREVIOUS_BUNDLE` можно
передать предыдущую сборку с той же командой регистрации обработчика. По умолчанию сценарий
создаёт и подписывает учебную предыдущую сборку из переданного приложения.

```sh
AGENT_WATCH_TEST_BUNDLE=/path/to/AgentWatch.app task test-git-upgrade
```

После замены приложения оба клиента сохранили прежнюю запись. Для удаления `release` окно
показало первый из двух шагов, для `feature/example` — единственный шаг. Пока комплекта не было
на месте, оба клиента получили отказ «the installed hook could not run», а после возврата снова
показали окно подтверждения. Файлы профилей, решение о доверии Codex и настройки Git совпали
побайтно, ссылки учебного сервера сохранились (замер: Claude Code 2.1.326,
Codex 0.171.0-alpha.13, macOS 26.6.2).
Загрузку выпуска и его установку через Sparkle проверяет отдельный сценарий `task e2e-update`.

Готовый исполняемый файл Rust для проверки закрытия чата можно передать через
`AGENT_WATCH_TEST_GIT_BIN`.

```sh
task test-cli-close
```

Тест дожидается видимого окна macOS, связанного с процессом этого запроса. Затем Claude Code
останавливает целевой разговор по его идентификатору, сохраняя второй разговор активным. Codex
архивирует целевой чат и проверяет его в списке архивных. После этого сценарий сверяет все ссылки
репозитория на сервере и проверяет исчезновение окна и обоих процессов Rust. Уборка начинается
после этих проверок. В обоих клиентах целевая ветка осталась на месте, окно закрылось,
исполнитель и процесс окна завершились (замер: Claude Code 2.1.326, Codex 0.171.0-alpha.13,
macOS 26.6.2). Обычное переключение на соседнюю вкладку и закрытие окна настольного
приложения имеют другую семантику и этим тестом не покрыты.

## Сквозная проверка в Codex

В этой проверке Mothership передавал запрос на подтверждение Agent Watch.

19 ноября 2026 года в обычном чате Codex `push_once` вернул `completed` после того, как
пользователь подтвердил удаление тестовой ветки в окне Agent Watch сборки `6ac27a52`
(замер: Codex 0.169.0-alpha.11.1, macOS 27.2). Затем `git ls-remote` подтвердил, что тестовой
ветки в `origin` больше нет и основная ветка осталась на исходном коммите.

## Подготовка проверки в настольном клиенте Windows

Потребуются Git и Python 3.9 или новее. Выберите свободное имя папки на локальном диске.
Обе команды выполняются из исходной папки Agent Watch.

```powershell
py -3 scripts/desktop_git_fixture.py prepare "$env:TEMP/agent-watch-desktop-example"
py -3 scripts/desktop_git_fixture.py status "$env:TEMP/agent-watch-desktop-example"
```

Команда `prepare` создаёт отдельный проект и соседний локальный сервер Git. Команда `status`
сверяет ссылки сервера с исходными значениями. Код 0 означает полное совпадение, 1 — изменение,
2 — ошибку проверки.

Исполнитель с окном подтверждения поставляется для macOS. Проверка настольных клиентов Windows
остаётся в [плане](implementation-plan.md).
