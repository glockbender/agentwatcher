# Agent Watch для работы с проектами

Здесь собраны решения о развитии продукта, их цена и порядок проверки. План выпуска существующей версии ведётся отдельно.

<details class="context" open markdown="1">
<summary>Почему одного списка сессий стало мало</summary>

В терминале внутри среды разработки Agent Watch помогает найти вкладку, где агент ждёт ответа. В настольных приложениях Claude и ChatGPT уже есть списки чатов. При работе с обоими агентами остаются общие вопросы. Какие сессии относятся к одному проекту? Что им разрешено делать с его ветками? Можно ли освободить место после сборки и через неделю вернуться к чату? За ответами сегодня приходится идти в разные приложения.

</details>

> **Коротко.** Предлагаю дать человеку возможность открыть проект в Agent Watch, увидеть правило удаления ветки на сервере, изменить его и проверить на примере. Параллельно стоит проверить общую для Claude и Codex страницу проекта и запуск той же защиты из настольного клиента Windows.
>
> Mothership остаётся полигоном. После переноса Agent Watch отвечает за установку и работу функции. Первым вложением станет защита Git. Вторым я бы выбрал менеджер рабочих копий: для него уже известен случай, когда место удалось вернуть и сохранить сами копии.

## Что можно попробовать в рабочей версии

В настройках Mac можно выбрать репозиторий и потребовать ввод его имени при удалении конкретной ветки с сервера. Когда правило больше не нужно, его можно снять. Общий список веток действует во всех рабочих копиях репозитория.

Защита прошла отдельную проверку в чистых профилях Claude Code и Codex. При отмене запроса и при разрыве связи ветки остались на месте. Обычное создание ветки обработчик пропустил. Эта проверка охватывает командные клиенты и тестовый сервер Git. Для перехода с Mothership есть отдельная проверка двух пакетов: она замечает двойную регистрацию защиты и потерю другого обработчика. Перед выпуском предстоит проверить подтверждение человеком в настольном чате и переход действующей установки Mothership с сохранением остальных защит.

В меню Mac появилось окно **Projects & Recent…**. Оно ведёт в наблюдаемые чаты двух агентов, объединяет рабочие копии одного проекта и показывает последние известные лимиты по папкам агентов. В настройках **Working Copies** можно найти каталоги сборки и открыть их в Finder. У каждой рабочей копии видно, встречается ли её коммит в известной Git истории удалённых веток. Ещё предстоит проверить, какие из них можно убрать во время работы агентов.

Для доверенной программы проверены повторный запуск и отказ после замены файла. Опыт использует вымышленное значение. Запросы самой Связки ключей и работа двух настольных клиентов на Windows остаются отдельными испытаниями. Для Windows подготовлен учебный проект с локальным сервером, где после отмены можно сверить каждую ветку. Приведённые ниже оценки относятся к исходному объёму работ.

## Правило Git на примере одной ветки

Предположим, Claude собирается удалить ветку `release` на сервере. Сегодня Mothership уже останавливает такую команду, если она требует подтверждения. Новая польза появляется **до запроса**: можно выбрать проект и увидеть, почему в нём сработает конкретное правило.

1. В разделе проекта «Защита» видно общее правило для Claude и Codex и исключения этого проекта. Например, для удаления обычной ветки достаточно подтверждения. Для ветки `release` дополнительно требуется ввести имя репозитория.
2. Человек выбирает готовый уровень и видит образец будущего запроса с названием ветки, репозитория и адресом назначения. Просмотр примера ничего не меняет в Git. Настройку сохраняет сам человек.
3. При реальной попытке удаления проверка перед командой направляет агента к инструменту MCP (протоколу вызова внешних инструментов). Инструмент запрашивает подтверждение в исходном чате. Непосредственно перед исполнением он сверяет версию ветки и применимое правило. Если ветка изменилась, прежнее согласие теряет силу.

В первом переносе я бы сохранил действующие минимальные требования к защищённым веткам. Общая настройка задаёт поведение для всех проектов, исключение усиливает его для выбранной ветки. Ослабление защиты потребует отдельного решения. Закрытое окно Agent Watch не должно мешать работе. Если недоступен сам инструмент подтверждения, защищённая операция останавливается с понятным объяснением. Сбой наблюдения за сессиями по-прежнему позволяет агенту продолжить работу.

<details class="more" markdown="1">
<summary>Как проверить передачу функции из Mothership</summary>

Проверить на чистой установке и при переходе с Mothership. В обоих случаях обычная операция проходит, защищённая вызывает ровно один процесс подтверждения, отказ сохраняет ветку. При передаче владения сначала проверяется новая установка, затем отключается старая регистрация. Сбой на середине должен оставлять работающую защиту и понятный путь восстановления. Испытания выполняются на отдельном тестовом репозитории.

У Mothership есть и другие проверки. Следующий кандидат — удаление файлов с показом пути, размера и последствий. Запрет бесконечной записи в файл уже полезен как автоматическая проверка. Основания для отдельного окна у него пока нет. Напоминание о языке ответа и проверка установки самого Mothership принадлежат своему продукту. ## Проекты и недавние сессии

**Проект — локальный репозиторий со всеми его рабочими копиями** (`git worktree` позволяет работать в нескольких папках одного репозитория одновременно). В дереве проекта рядом видны сессии Claude и Codex, их ветки и папки. Размещение копии внутри репозитория удобно для навигации, но потребовало бы договариваться о расположении с каждым настольным клиентом. Git уже хранит связь между папками. Её можно использовать и для копии, созданной самим клиентом в другом месте. Имя папки служит подписью: два разных проекта с папкой `src` должны оставаться разными. [Как Git связывает рабочие копии](https://git-scm.com/docs/git-worktree)

**«Недавние» — короткий общий вход в работу.** Вверху текущие сессии, ниже — завершённые, к которым ещё можно вернуться. Внутри каждой части действует знакомый порядок Agent Watch по последней активности сессии. Архивирование в исходном клиенте должно убирать запись из этого списка, когда состояние архива можно достоверно прочитать. Объём раздела ограничен. Конкретное число строк лучше подобрать на собственных сессиях по тому, сколько прокрутки требуется, чтобы найти нужную.

Над списком — быстрые фильтры «Все», «Работают», «Ждут ответа» и «Давно без активности». Последний показывает время и последнее известное действие. Даже несколько минут тишины могут означать нормальную работу. Щелчок открывает точный чат, когда известна его ссылка. Для завершённой беседы одного названия мало. До включения такого чата в «Недавние» нужно подтвердить на каждом клиенте, что после перезапуска открывается именно он. Если клиент умеет вернуть только на главную, список охватывает лишь те чаты этого клиента, к которым подтверждён возврат. Обычный виджет и переход в терминал остаются полезны во время работы в среде разработки.

<details class="more" markdown="1">
<summary>Почему одним изменением сортировки здесь не обойтись</summary>

Сейчас подпись проекта может быть последней частью пути. Текущая история восстанавливает открытые сессии и исключает закрытые. Поэтому предстоит отдельно проверить принадлежность сессии проекту и возможность открыть завершённый чат после перезапуска. Достаточная проверка — два репозитория с одинаково названными папками, рабочая копия вне репозитория, оба агента и по завершённому и архивированному чату в каждом клиенте. Неизвестная папка остаётся без привязки до появления достоверных сведений. ## Сколько места можно вернуть

В разборе «Быстрое заполнение диска» очистка результатов сборки в 13 рабочих копиях вернула около 31 ГБ без удаления самих копий. В другом разборе Claude продолжал учитывать копии, папки которых уже удалили. Эти два наблюдения определяют, что стоит показать человеку перед действием.

| Что видит человек | Что может сделать |
|---|---|
| «Идёт сборка», название сессии и ветка | Открыть сессию и вернуться к очистке позже. |
| «Сборка занимает место», размер и причина, по которой очистка доступна | Убрать воспроизводимые результаты сборки. Исходники и рабочая копия остаются. Следующая сборка займёт больше времени. |
| «Есть изменения только в этой копии», причина и путь | Открыть папку и разобраться с изменениями. Действие удаления недоступно. |
| «Копией управляет Claude» или «Копией управляет Codex» | Перейти к действиям исходного приложения. Для обычной завершённой копии отдельно проверить возможность удаления. |

Сверху нужны две цифры — сколько занимают сборки и сколько сейчас можно очистить. Возле действия нужны подпись риска, причина и ожидаемый результат. Цвет и значок помогают заметить предупреждение. Если часть проверок не удалась, строка показывает «Не удалось проверить» и предлагает повторить проверку. Перед очисткой состояние проверяется заново. Для перемещения в Корзину стоит прямо сказать, что свободное место появится после её опустошения.

## Подписки и доступ к секретам

У подписки своя граница — **учётная запись**. Лимит одного профиля может расходоваться в нескольких проектах. Предлагаю отдельный обзор профилей с остатком лимита, временем очередного обновления и расходом в токенах (единицах обработанного текста). Расход по моделям полезен как подробность. Календарь рабочих дней, график тенденций и расход по проектам можно отложить. Если позже появится денежная оценка по расценкам модели, её нужно явно отличать от фактической платы за подписку.

**Досрочное восстановление лимита Codex** расходует одну доступную попытку. В Vorssaint уже есть дополнительное подтверждение. Улучшение для Agent Watch — показать последствия до первого нажатия: выбранный профиль, остатки текущего и недельного лимитов, дату планового обновления, число доступных попыток сейчас и после операции. Если профиль или результат прошлой попытки неизвестен, сначала обновить данные. [Что делает восстановление в Vorssaint](https://github.com/vorssaint/vorssaint-utils/blob/v3.4.4/Sources/Vorssaint/Core/NotchAgentStrings.swift#L263-L278)

**У секретов граница другая — доверенная программа.** В проекте музыкального бота три отдельные записи в Связке ключей (системном хранилище учётных данных macOS) могли вызывать три запроса при запуске. В проекте объединили нужные программе данные в одну запись, которую бот читает один раз. Это уменьшает число обращений. Будет ли система спрашивать пароль при следующем запуске, зависит ещё и от разрешений программы. [Решение проекта бота](https://github.com/glockbender/svalka-muz-repostov-tgbot/blob/main/openspec/changes/archive/2026-11-18-keychain-credential-bundle/proposal.md) · [Как macOS запоминает разрешение](https://support.apple.com/guide/mac-help/kychn002/mac)

Первый сценарий — подключить проект к системному хранилищу, выбрать доверенную программу и повторно запустить её. В карточке достаточно названия подключения, назначения и состояния доступа. Секрет читает сама выбранная программа. Он не проходит через аргументы запроса агента, ответ инструмента или журнал приложения. Доверие относится и к сценариям, и к подключаемым модулям. Даже подписанный интерпретатор может выполнить изменённый сценарий, который напечатает секрет. Для первого примера подойдёт заранее выбранная программа с проверяемым составом кода и ограниченным ответом о результате. Повторный запуск изменённого кода требует пересмотра разрешения. Давать агенту произвольное чтение записей или переносить значения через чат для этого не требуется. Отдельную возможность переноса из файлов стоит обсуждать после проверки запуска. На Windows есть Диспетчер учётных данных. Его разрешения и поведение при повторном запуске придётся проверить на этой системе. [Системное хранилище Windows](https://learn.microsoft.com/en-us/windows/win32/api/wincred/)

## Нативные окна и настольные клиенты Windows

На Mac я бы начал с одного обычного окна проекта с боковой панелью, поиском, переходами с клавиатуры и стандартным подтверждением опасного действия. В настройках Agent Watch уже используется SwiftUI (средство Apple для построения интерфейсов), а плавающий виджет использует AppKit (средство управления окнами macOS). Можно улучшить нужное окно и проверить удобство на двух действиях: открыть ожидающий чат с клавиатуры и понять последствия очистки до подтверждения. Перерисовка всего приложения увеличила бы первый выпуск. [Существующее окно настроек](https://github.com/glockbender/agentwatcher/blob/main/Sources/AgentWatchApp/SettingsWindowController.swift)

На Windows первым испытанием должна стать защита Git **в установленных настольных клиентах**. Открыть тестовый проект в каждом, проверить получение события, запрос подтверждения, отмену и один подтверждённый результат. Записать версию клиента и фактическую среду выполнения Git. Результат из отдельно запущенного терминала не отвечает на этот вопрос. Сегодня запуск и установка инструмента Mothership зависят от системных функций Unix. Если один клиент не поддерживает нужный шаг, зафиксировать границу поддержки для этого клиента до оценки полноценного переноса. [Как запускается инструмент](https://github.com/glockbender/mothership/blob/main/plugins/mothership/native/src/process.rs)

Режим у выреза камеры имеет смысл как отключённый по умолчанию способ заметить ожидающий запрос. Возможность удерживать Mac от сна в один щелчок уже даёт Vorssaint. Возвращаться к ней в Agent Watch стоит ради конкретной задачи, например «пока выполняется эта сборка», если у задачи надёжно определяется завершение. [Возможности Vorssaint](https://vorssaint.com/)

## Что изменилось после независимого разбора

Рецензент поддержал перенос защиты по одной операции. У удаления ветки уже есть проверяемый результат для согласия, отказа и изменения ветки во время подтверждения. У очистки диска отдельное достоинство — пользу можно измерить возвращённым местом при сохранённой рабочей копии.

После разбора в предложение вошли три условия. Завершённый чат попадает в «Недавние» после проверки точного перехода. Поддержка Windows оценивается по реальному запуску из каждого настольного клиента. Разрешение на доступ к секрету относится ко всему запускаемому коду, включая сценарии. Эти проверки могут уменьшить первый выпуск и напрямую влияют на оценку.

## Вехи и первая задача

1. **Просмотр защиты Git на Mac.** Первая задача реализована в рабочей копии. В настройках на странице `Git Protection` выберите папку проекта и введите `release`. Видно, требует ли локальное правило ввода имени репозитория и когда ответ зависит от основной ветки сервера.
2. **Настройка и исполнение защиты.** Уровень для одной ветки уже можно изменить. Форма запроса проверена на отдельном репозитории. До завершения вехи остаются проверка одобренного действия в настольном чате и переход действующего профиля с Mothership.
3. **Испытание на Windows.** Параллельно с работой на Mac проверить один запрос в обоих настольных клиентах. Решение о поставке зависит от результата.
4. **Проекты и недавние сессии.** Найти по проекту нужный чат любого агента, открыть его после перезапуска и проверить архивирование.
5. **Рабочие копии и место.** Увидеть, что занимает диск, очистить результаты сборки и проверить сохранность исходников. Отдельно подтвердить пригодность удаления целой копии.
6. **Подписки.** Увидеть лимиты двух профилей, затем проверить предварительный просмотр и подтверждение досрочного восстановления.
7. **Доверенная программа.** Подключить один проект к системному хранилищу и повторно запустить программу с проверенным доступом.

## Стоимость и порядок работы

Ниже моя предварительная оценка труда одного разработчика, знакомого с обоими проектами. Рабочий день включает реализацию и проверку. Диапазоны нужны для выбора очередности. Сроки публикации, доступ к компьютеру Windows и ожидание внешних разрешений оцениваются отдельно.

| Часть | Оценка | Что покупает эта работа и где остановиться |

Первое вложение — **7–14 рабочих дней труда** на перенос Git на Mac и проверку Windows. Это две задачи, которые можно исследовать параллельно. Для работы над списком проектов и очисткой общая зависимость одна — достоверная связь сессии, репозитория и рабочей папки. Один поток работ определяет эту связь, а другой может независимо проверить объяснения риска на уже известных случаях. Подписки и секреты можно исследовать отдельно, не расширяя первый выпуск.

Цена дальнейшего развития — поддержка изменений двух настольных клиентов на каждой заявленной системе. Оставить функции в Mothership дешевле сегодня, но тогда пользователю приходится устанавливать отдельный инструмент и выяснять правила проекта вручную. Перенос даёт одно место для настройки и объяснения решений. Его ценность стоит оценивать после первого законченного сценария, прежде чем обещать весь перечень.
