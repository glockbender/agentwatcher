# План до 1.0

Здесь — что осталось до версии 1.0, условия, при которых каждый шаг считается сделанным, и работа
над ближайшим релизом. 1.0 — это установка, для которой человеку достаточно скачать образ и
перетащить приложение. Это единственный такой список; после выпуска 1.0 документ уходит. Чего здесь
нет: этапы продукта и открытые продуктовые решения — в [плане реализации](implementation-plan.md);
как сейчас собирается, подписывается и обновляется релиз — в [distribution.md](distribution.md).

## Что уже есть

- Детерминированный мониторинг Claude Code и Codex, виджет, меню сессий, настройки оформления,
  порядка и сочетания клавиш, сохранение истории, переход к сессии, самообновление.
- Установка и снятие интеграций со страницы Tooling в настройках; сохранение чужих хуков и
  статусной команды.
- Новый мастер: выбор агента → подключение → проверка сигнала; доступ с пустого виджета и
  `Tooling → Set Up Again…`. Повторение ничего не удаляет. Внешний вид и сессии сохраняются.
- Признаки найденной программы отдельно от состояния подключения. Ошибки записи видны в окне.
- README с настоящими AppKit-изображениями на вымышленных данных и роликами, снятыми в чистой
  macOS внутри виртуальной машины.
- Плагин IDE: classic/reworked terminal, ping, тесты, verifier, CI подписи и публикации.
- Стабильный выпуск: 0.3.0 опубликован 2026-10-08 без пометки pre-release, и самообновление его
  видит. Дальше релизы выходят так же, оставаясь на 0.x до 1.0.

Это готовность отдельных частей, а не заявление о проверенной чистой установке всего продукта.

## Ближайший релиз: 0.4.0

В нём, кроме фич, накопленных после 0.3.0, — changelog, окно обновления со списком изменений и
скилл, который ведёт релиз. Решения приняты 2026-10-10.

**Принято при любом исходе пробы Sparkle:**

- Changelog пишется для человека, который обновляет приложение: только то, что он заметит, и что
  ему сделать. Рефакторинг, тесты и документы туда не попадают.
- Единственный источник — `CHANGELOG.md` в корне, на английском, разделы Added / Changed / Fixed.
  Раздел версии идёт в текст релиза над инструкцией по установке. `release.yml` не начинает сборку,
  когда раздела для версии тега нет. Раздел вырезает скрипт в `scripts/` с тестом и пределом слов
  на пункт.
- Текст пишется при релизе, из коммитов с прошлого тега. Исключение — изменение, после которого
  человек должен что-то сделать: его пункт пишется сразу, в `## [Unreleased]`.
- История: короткий раздел 0.3.0 (изменения с 0.1.0) и строка о 0.1.0. Их сборка — пробный прогон
  скилла.
- Ролики для релиза отдельно не снимаются: пункт ссылается на раздел README, закреплённый за
  тегом (`…/blob/vX.Y.Z/README.md#…`).
- Текст изменений плагина IDE остаётся в `plugin.xml`; в changelog приложения плагин попадает одним
  пунктом, когда к релизу приложен новый файл плагина.
- Скилл `.claude/skills/release/` ведёт только приложение. Маршрут: проверки → коммиты с прошлого
  тега → раздел → **один вопрос владельцу: раздел, версия, идём до черновика** → коммит версии →
  пуш `main` и тега → `release.yml` → проверка черновика → **публикация после «да»** → проверки
  после публикации. Хук `git-guard` спрашивает на пуше в `main` сам, и скилл его не обходит.
- Перед тегом zip кандидата распаковывается, и на нём выполняется ровно
  `codesign --verify --strict`: этой проверкой установленные 0.3.0 решают, принять ли обновление.
- Обновление проверяется в виртуальной машине перед тегом, против локального сервера, который
  изображает релиз. Негативные случаи: сети нет, сервер молчит, ответы 500 и 403, обрыв посреди
  архива, неверная контрольная сумма, битая подпись, папка без права записи, повтор после сбоя.
  В каждом — установленная копия не изменилась, временных папок не осталось, следующая проверка
  работает. После публикации в машине настоящий 0.3.0 обновляется до 0.4.0.

**Зависит от пробы Sparkle.** Код Sparkle 2.10 (`SUUpdateValidator.m`) принимает обновление, если
верна хотя бы одна из подписей, EdDSA или Apple, а целая ad-hoc подпись новой копии допустима.
Проба подтверждает это в машине и проверяет: `codesign --verify --strict` на бандле со
`Sparkle.framework`; нет уведомления macOS о запрете менять приложения; показан список изменений за
несколько версий; бандл собирает `build-app.sh`; запуск из Xcode работает без ручных шагов.

| | Проба прошла | Не прошла |
|---|---|---|
| Обновление | Sparkle: прогресс, отмена, список изменений в его окне | своё: прогресс-бар, список изменений, повтор |
| Откуда список изменений | описание в `appcast.xml`, приложенном к релизу | `CHANGELOG.md`, приложенный к релизу |
| `AppUpdater`, `UpdateText`, `task e2e-update` | удаляются | остаются; у `e2e-update` устарел тег по умолчанию `v0.1.0` |
| ADR | Sparkle и его настройки приватности | своё обновление; Sparkle — вместе с Developer ID |

**Открытые решения, с тем, что принято по умолчанию:**

- Как фид Sparkle несёт изменения за несколько версий. По умолчанию: одна запись, в её описании
  весь `CHANGELOG.md`, а делегат оставляет разделы новее установленной версии.
- Собственный вопрос Sparkle «проверять автоматически?». По умолчанию его нет: проверками управляет
  существующая настройка `Check for updates on launch`.
- Что остаётся от обновления в проверке пуша, если `AppUpdater` удалён. По умолчанию — ничего:
  обновление проверяет прогон в машине при релизе, и проверка пуша его больше не покрывает.

  скрипт с тестами. Ключ EdDSA в секретах CI заводит владелец.
- [ ] История в `CHANGELOG.md` как пробный прогон скилла; правила скилла правятся по его итогу.

## Что не блокирует 1.0

Watchdog зависаний, Ollama/LLM-функции, локальная статистика, Intel/universal.
Это следующие продуктовые этапы, а не долг перед 1.0. Автоматически давать
доверие хукам за пользователя не требуется: явный шаг и проверяемая доставка достаточны.
