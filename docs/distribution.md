# Дистрибуция

## Требования

Исходные заметки, дословно. Ниже — что из них закрыто и как устроено то, что уже есть.

- дистрибуция пока только через сбор установочного пакета и его публикация инструментами гитхаба
  - при этом надо придумать как сделать проверку обновлений
    - при появлении новой версии, при запуске тула всегда просить обновиться с возможностью отказаться от обновления
- нужно четко выделить логику первого запуска
  - окно всегда по центру основного экрана, т.к. оно мелкое и легко его не найти, еще не освоившись с тулом
  - нужно встроить установку в агентские тулы в самом приложении. 
    - Тул пока должен нести с собой плагин с актуальными скриптами хуков и всей необходимой интеграцией. 
    - При явной проверке установленных тулов в первый запуск 
      - проверка должна выполняться вообще при каждом новом запуске тула, не только при первом
      - попросить пользователя сначала установить необходимую обвязку. 
        - для каждого тула явно предлагать согласиться на установку
        - если это не первый запуск, но проверка показала новый установленный тул, показать список установленных и неустановленных и дать явно установить. 
        - запомнить выбор, и триггернуть его еще раз только при появлении новго тула. 
        - при этом в меню должна быть эта настройка, если вдруг выбор захочется изменить

## Что из этого закрыто

- **Сбор пакета и публикация средствами GitHub** — сделано, устройство ниже.
- **Установка интеграций внутри приложения** — сделана окном тулинга: hooks и статус-строка для
  Claude Code и Codex, секция `IDE integrations` для плагина JetBrains.
- **Проверка обновлений** — сделана, вместе с установкой обновления самим приложением; устройство —
  в [архитектуре](architecture.md) §11.
- **Логика первого запуска** (окно по центру, предложение установить интеграции при каждом запуске,
  запомненный выбор, та же настройка в меню) — нет.

## Поддерживаемая платформа

Первый релиз предназначен только для Apple Silicon (ARM64), macOS 14 и новее.
Intel и universal-бандл в объём релиза не входят. Сборка релиза выполняется на ARM runner.

## Что такое релиз

Тег `vX.Y.Z` запускает `.github/workflows/release.yml`, и тот оставляет **черновик** релиза с двумя
файлами:

- `AgentWatch-<версия>.zip` — бандл приложения, упакованный `ditto`. Это единственный архиватор,
  сохраняющий символические ссылки и расширенные атрибуты бандла, а с ними и подпись: замерено —
  после распаковки `codesign --verify` проходит;
- `AgentWatch-<версия>.zip.sha256` — контрольная сумма в формате, который понимает `shasum -c`.

Черновик, а не публикация: что написано в примечаниях и увидит ли это мир — решение человека.

Локально то же делает `task release` (`scripts/release.sh`): собирает бандл в release-конфигурации,
кладёт zip и сумму в `dist/` и печатает, чем подписал.

## Версия

Единственный источник — `CFBundleShortVersionString` в `Resources/Info.plist`. Из него же при сборке
бандла пишется `CFBundleVersion`: по нему macOS решает, какая из двух копий новее, и константа в нём
делает все сборки одинаковыми на вид. Проверка обновлений сравнивает `CFBundleShortVersionString`
(`AppUpdater.version(ofBundleAt:)`), а по `CFBundleVersion` две копии различает сама macOS.

Workflow первым делом сверяет тег с этим значением и падает при расхождении, ничего не собрав.
Релиз, у которого имя файла и окно «О программе» говорят разное, находит только тот, кто его скачал.

## Подпись: где мы сейчас

Релиз подписан **ad-hoc** — подписью без сертификата. Что это значит, замерено:

```
spctl --assess --type execute  →  rejected
```

Gatekeeper отвергает такой бандл независимо от карантина: он смотрит на подпись, а флаг
`com.apple.quarantine` решает другое — будет ли вообще проверка при первом запуске. Поэтому рабочая
инструкция для скачавшего одна:

```sh
xattr -dr com.apple.quarantine /Applications/AgentWatch.app
```

Обход через Finder («Control-click → Open») в macOS 15 убран; остался путь через
System Settings → Privacy & Security → Open Anyway, и для приложений без Developer ID он срабатывает
не у всех. Команда выше работает всегда — проверено: после неё из атрибутов остаётся только
`com.apple.provenance`, который macOS ставит себе сама.

Сертификат `Agent Watch Developer` из `scripts/build-app.sh` в релиз **не идёт**. Он самоподписанный
и нужен для другого — чтобы macOS не теряла выданные разрешения при каждой пересборке (разбор — в
комментарии самого скрипта, как его завести — в `AGENTS.md`). Скачавшему он не говорит ничего, поэтому `release.sh` берёт только идентичность, названную
явно в `AGENT_WATCH_RELEASE_IDENTITY`, а иначе подписывает ad-hoc и предупреждает об этом.

## Что нужно для нотаризации

Нотаризация (Apple проверяет бандл у себя и ставит отметку, после которой macOS открывает его молча)
— это связка из четырёх вещей, и она упирается в платную Apple Developer Program:

1. сертификат **Developer ID Application** — выдаётся только участнику программы (99 USD в год);
2. **hardened runtime** (`codesign --options runtime`) — без него бандл на нотаризацию не принимают;
3. **entitlement** `com.apple.security.automation.apple-events` — hardened runtime запрещает Apple
   Events, а на них держится переход к вкладке терминала (`NSAppleEventsUsageDescription` в
   `Info.plist` ровно про это). Без entitlement функция молча перестанет работать, поэтому hardened
   runtime включается вместе с нотаризацией, а не раньше;
4. `xcrun notarytool submit --wait` с учётными данными в keychain-профиле
   (`notarytool store-credentials`), затем `xcrun stapler staple` — отметка прикрепляется к бандлу,
   чтобы он открывался и без сети.

Пока сертификата нет, этот код нечем проверить, поэтому его нет и в `release.sh`.

## Плагин IDE в релизе

Плагин версионируется отдельно от приложения и в бандл не вкладывается (разбор — в
[плане](implementation-plan.md)). В релиз он попадает отдельным файлом, и **имя файла — контракт**:
`agent-watch-ide-<версия>.zip`. Его разбирает `IDEPluginInstallation.stagedPlugin`, когда решает,
какой файл предлагать IDE, и по нему же сравнивает версии.

Релизный workflow приложения его не собирает. В релиз идёт тот же файл, что ушёл на Marketplace:
`publish-plugin.yml` (раздел ниже) подписывает его и оставляет артефактом запуска уже под именем
из контракта, так что в релиз он кладётся как есть:

```sh
gh run download <run-id> --name agent-watch-ide --dir ide-plugin/build/signed
gh release upload vX.Y.Z ide-plugin/build/signed/agent-watch-ide-<версия>.zip
```

`<run-id>` — номер запуска `publish-plugin` из `gh run list --workflow publish-plugin`; без него
команда спросит его сама.

Локальная сборка `task plugin` — для проверки на этой машине, не для релиза: подписи в ней нет. Она же
кладёт файл туда, откуда приложение предлагает плагин IDE, под тем же именем, что у подписанного
релиза, — поэтому проверка перед push (`task plugin-check`) собирает и тестирует плагин, но не кладёт.

## Плагин IDE в Marketplace

Marketplace — основной путь установки плагина (почему — в [плане](implementation-plan.md)), и он
оформлен так, что подписывать и публиковать умеет CI, а секреты в репозиторий не попадают.

**Что проверяет Marketplace и где это лежит.** Идентификатор, имя, `<vendor>` с почтой и сайтом,
описание и заметки о версии — в `ide-plugin/src/main/resources/META-INF/plugin.xml`; логотип —
`pluginIcon.svg` и `pluginIcon_dark.svg` рядом, 40×40 с двухпиксельным прозрачным полем; лицензия —
`LICENSE` в корне, при загрузке выбирается MIT и даётся ссылка на исходники. Имя не должно содержать
слов `Plugin`, `IntelliJ`, `JetBrains` и названий продуктов ([правила
имени](https://plugins.jetbrains.com/docs/marketplace/best-practices-for-listing.html)). Идентификатор
— полное имя в стиле Java-пакета из букв, цифр, `.`, `-` и `_`, и после публикации он не меняется
([правила `<id>`](https://plugins.jetbrains.com/docs/intellij/plugin-configuration-file.html#idea-plugin__id));
verifier Marketplace предупреждает о шаблонных словах в нём — `plugin`, `intellij`, `jetbrains`, `idea`
— поэтому выбран `com.glockbender.agentwatch`, без них. Совместимость до загрузки проверяет
`./gradlew verifyPlugin` (на 0.1.4 — `Compatible`); имя и идентификатор проверяет сам Marketplace.

**Подпись.** Gradle-плагин сам читает три переменные окружения — `CERTIFICATE_CHAIN`, `PRIVATE_KEY`,
`PRIVATE_KEY_PASSWORD` — и когда они заданы, `signPlugin` срабатывает перед `publishPlugin`.
Единственная настройка в `build.gradle.kts` — куда и под каким именем ложится подписанный файл:
`build/signed/agent-watch-ide-<версия>.zip`, то же имя, что в контракте релиза. Ключ принимается в любом виде, который выдаёт OpenSSL 3:
зашифрованный PKCS#8 с паролем, PKCS#8 и PKCS#1 без пароля — проверено одноразовым ключом.
`verifyPluginSignature` той же версии Gradle-плагина (2.18.1) подставляет содержимое цепочки туда,
где утилита ждёт путь к файлу, и падает; подпись всё равно проверяет Marketplace при загрузке.

Ключ делает человек, один раз, вне репозитория. Пароль OpenSSL спрашивает сам, так что в историю
команд он не попадает:

```sh
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -aes-256-cbc -out private.pem
openssl req -key private.pem -new -x509 -days 3650 -subj "/CN=glockbender" -out chain.crt
```

Десять лет, а не год из примера в документации: сертификат самоподписанный, и нужен Marketplace
только чтобы убедиться, что файл не подменили по дороге, — так что срок его действия лишь
назначает день, когда публикация внезапно перестанет работать.

Три значения уходят в секреты GitHub (Settings → Secrets and variables → Actions) под теми же
именами — `gh secret set NAME < file` читает файл целиком, многострочные значения допустимы, — и в
менеджер паролей как единственную копию; файлы после этого удаляются. До первой загрузки ключ ни
с чем не связан: потерянный пересоздаётся теми же двумя командами, и секреты переписываются.
Четвёртый секрет, `PUBLISH_TOKEN`, — токен из раздела My Tokens профиля на Marketplace; он
появляется после первой загрузки.

**Первая версия — руками.** Marketplace принимает первую версию только через сайт: там выбираются
лицензия, ссылка на исходники и теги и создаётся профиль вендора, а `publishPlugin` требует, чтобы
плагин уже существовал. Порядок:

1. Подписать в CI, где лежит ключ: `gh workflow run publish-plugin.yml` запускает тот же
   workflow без тега, и он только собирает, проверяет и подписывает, а подписанный файл
   оставляет артефактом запуска — `gh run download --name agent-watch-ide`. Ключа на ноутбуке при
   этом нет. Локальный `./gradlew signPlugin` с тремя переменными в окружении — запасной путь, не
   основной.
2. На plugins.jetbrains.com войти под аккаунтом JetBrains, в профиле — Add new plugin. Профиль
   вендора создаётся там же: публичное имя, почта и сайт — те же, что в `<vendor>`; идентификатор
   вендора потом не меняется. Там же — декларация trader или non-trader: по документации trader —
   тот, кто действует в рамках своего ремесла, бизнеса или профессии, и бесплатность плагина сама
   по себе этого не решает; статус — заявление самого человека.
3. Принять Developer Agreement, выбрать лицензию MIT и указать ссылку на исходники, хотя бы один
   тег, канал по умолчанию, загрузить файл.
4. Ждать письма: каждую версию проверяют люди, о смене статуса приходит уведомление; если за 3–4
   рабочих дня ничего — писать на marketplace@jetbrains.com.
5. После одобрения — My Tokens → Generate Token → секрет `PUBLISH_TOKEN`.

**Следующие версии — тегом.** Поднять `version` в `ide-plugin/build.gradle.kts`, закоммитить и
поставить тег `plugin-v<версия>`: `.github/workflows/publish-plugin.yml` сверяет тег с версией,
собирает против скачанной IDE, прогоняет тесты и `verifyPlugin`, подписывает, публикует и оставляет
подписанный файл артефактом. Каждая версия снова проходит ревью, так что на Marketplace она
появляется не сразу.

**Смена идентификатора.** До публикации идентификатор был `com.glockbender.agentwatch.ide`, затем
`…plugin.jetbrains`; с 0.1.4 — `com.glockbender.agentwatch`: после публикации менять его нельзя, а
слова `plugin` и `jetbrains` verifier помечает как шаблонные. Для IDE это другой плагин: копию со
старым идентификатором надо удалить в Settings → Plugins до установки новой, иначе на адрес
`agent-watch` окажутся подписаны два плагина.

## Чего ещё нет

- **Скачивания файла плагина из приложения.** Читающая сторона уже есть — каталог
  `~/Library/Application Support/AgentWatch/ide-plugin/`, — и адрес теперь тоже: плагин лежит в
  релизе рядом с приложением. Не хватает только кнопки, которая скачает его туда.
- **Образа для первой установки (`.dmg`)** — того самого окна с иконкой приложения и стрелкой на
  папку Applications. Пока раздаётся `.zip`. Обновление образ не использует и не будет: монтировать
  том ради замены бандла незачем.
- **Нотаризации** — см. выше.
- **Первого запуска как отдельного сценария** — требования в заметках выше, разбор по шагам в
  [плане](implementation-plan.md), этап 3.

## Проверки перед публикацией

`task verify-all` проверяет Swift, обе конфигурации сборки, бандл, опубликованный архив,
локальную сборку плагина и сквозное обновление. Последнее запускает отдельную копию приложения
с изолированными настройками и журналом; при сбое сохраняются ответ обновлятора и ошибка
автоматизации диалога. Нужны работающая основная копия приложения и Accessibility для терминала.

`task plugin-verify` дополнительно проверяет плагин на платформах 251 и 261. Workflow
`verify-plugin.yml` выполняет сборку, тесты и эту проверку на изменениях плагина в ветках и PR.
Проверка API не заменяет ручную проверку фокуса вкладок в работающей IDE.
