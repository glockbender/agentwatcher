# Фокус на конкретной сессии

## Задача

Переход к сессии из её строки в виджете (в то время — кнопка `↗`, теперь — клик по строке) должен
приводить к той самой сессии. На момент исследования он поднимал приложение целиком, и этого мало: в одном приложении открыто несколько окон, а в одном окне — несколько вкладок
с разными агентами. Нажатие даёт «где-то здесь», а не «вот эта сессия».

Документ разбирает варианты и заканчивается выбором, который нужно сделать. Все факты ниже — замеры
на этой машине (macOS 15.3.1, GoLand 2026.1.4, PyCharm 2026.1.4, Ghostty 1.3.1), а не предположения.

Документ переименован из «Фокус на конкретной сессии в JetBrains IDE»: терминал IDE остался основным
окружением, но не единственным — Ghostty идёт вторым, и способы для них разные. Требование к точности
поставлено прямо: **нужна вкладка, а не окно и не приложение.**

**Что из этого в коде, а что нет.** Замеры ниже верны, но не всё из них реализовано. Путь «бандл IDE
→ `dataDirectoryName` → `recentProjects.xml` → самое длинное совпадение пути» был написан и работал;
он давал карточке строку «the mcp-hub window», и когда та строка убрана как лишняя, разбор убран
вместе с ней. Чтение `product-info.json` осталось — но нужно оно самому Agent Watch: поле
`dataDirectoryName` называет каталог настроек IDE, а там лежит файл, которым плагин отвечает на
`ping`. Нужные окно и вкладку выбирает сам плагин, и join у него — номер процесса агента
(`jetbrains://<схема>/agent-watch/focus?pid=N`), а не эти файлы. Читать этот документ как список
того, что надо построить, — не стоит.

## Что изменилось с прошлой редакции

Три вещи, и каждая переставляет варианты местами.

**Одно утверждение было неверным.** «Заголовки окон читаются без разрешения» — не так. Замер был снят
из процесса, чьим ответственным приложением был GoLand, и померил разрешения GoLand, а не свои.
Подробности ниже; для выводов это значит, что бесплатного способа прочитать заголовок чужого окна
нет.

**Приложение научилось читать рабочий каталог процесса.** `AgentProcessScanner` уже вызывает
`proc_pidinfo(PROC_PIDVNODEPATHINFO)`, чтобы дать строку живому агенту, о котором приложение ничего
не слышало. Значит, полный путь проекта доступен **внутри** приложения по одному PID — и по проводу
он при этом не идёт. Возражение §15 к варианту с лаунчером снято.

**Ключ связи уже существует, и его никто не заводил специально.** Claude Code сам пишет в заголовок
терминала имя сессии — то самое `aiTitle`, которое приложение уже читает из транскрипта и показывает
в строке. В Ghostty этого хватает, чтобы найти вкладку, и в терминале JetBrains имя вкладки тоже
стоит. Но снаружи прочитать вкладку IDE нечем — ни словаря, ни доступного дерева, — поэтому там
ключом становится номер процесса, а достать его может только плагин.

## Что установлено замером

### Разрешения: что видно чистому приложению

Пробник — отдельный бандл `com.glockbender.agentwatch.focusprobe` с собственным bundle id, ad-hoc
подписью и без единого выданного разрешения; запускался через `open`, чтобы ответственным процессом
был он сам, а не терминал. Это и есть та ошибка, которую исправляет эта редакция: процесс, запущенный
из терминала, наследует разрешения приложения, которому терминал принадлежит.

| Что спросили | Ответ |
|---|---|
| `AXIsProcessTrusted()` | `false` |
| `CGPreflightScreenCaptureAccess()` | `false` |
| Всего окон в `CGWindowListCopyWindowInfo` | 44 |
| Из них с заполненным `kCGWindowName` | 2 |
| Окна GoLand и PyCharm | `name=<absent>` |
| `AXUIElementCopyAttributeValue(app, kAXWindowsAttribute)` | `-25211` (`kAXErrorAPIDisabled`) |

**Заголовок чужого окна требует разрешения Screen Recording** — с macOS 10.15 `kCGWindowName`
заполняется только процессам, которым оно выдано. Для приложения, которое следит за сессиями, это
худшее из возможных разрешений по восприятию: «Agent Watch хочет записывать экран» ради одной
строки в карточке.

**Что читается бесплатно** — владелец окна, его номер и прямоугольник. Из этого нельзя составить
подпись, но можно посчитать окна.

### Про сессию можно узнать всё, не спрашивая систему

JetBrains держит два файла, которые вместе отвечают на вопрос «в каком проекте эта сессия и открыт ли
он сейчас».

`<IDE>.app/Contents/Resources/product-info.json` называет каталог настроек этой сборки:

```json
{"name": "GoLand", "version": "2026.1.4", "productCode": "GO", "dataDirectoryName": "GoLand2026.1"}
```

`~/Library/Application Support/JetBrains/<dataDirectoryName>/options/recentProjects.xml` держит по
записи на проект, и ключ записи — путь проекта:

```xml
<entry key="$USER_HOME$/CommonProjects/instructions">
  <RecentProjectMetaInfo frameTitle="instructions – Commit: devx-672" opened="true" …>
    <option name="activationTimestamp" value="1788916626897" />
    <frame x="401" y="1146" width="740" height="838" extendedState="6" />
```

То есть путь, точный заголовок окна, признак «открыт» и время последней активации — без единого
разрешения. Цепочка целиком: PID агента → родительская цепочка (уже есть в `SessionHostRegistry`) →
бандл IDE → `dataDirectoryName` → `recentProjects.xml`; и отдельно PID агента → `proc_pidinfo` →
рабочий каталог → самый длинный совпадающий ключ.

**Оговорка, и важная: `opened="true"` не самоочищается.** GoLand 2025.2 числит открытыми 8 проектов,
хотя этой сборки нет в списке процессов. Признак говорит «так было, когда IDE последний раз сохраняла
состояние», поэтому его нужно скрещивать с «эта IDE сейчас запущена». Сам файл тоже пишется не
мгновенно: в момент замера ему был час.

**Правило «подняться до корня проекта» подтверждено:** у всех шести открытых проектов GoLand 2026.1
есть каталог `.idea/`. Но точнее не подниматься по дереву, а взять самый длинный ключ из
`recentProjects.xml`, который является префиксом рабочего каталога, — это тот же ответ, только
полученный от самой IDE.

### `open`: каталог — беда, файл — нет

Разобрано подробно, потому что первый замер дал неверный вывод об этом способе целиком.

**Каталогом — беда.** `open -a GoLand.app ~/CommonProjects/instructions` при **уже открытом** проекте:

```
05:17:37,002 ProjectUtil - Opening existing project with .idea at …/instructions
05:17:37,038 GlobalWorkspaceModel - Project instructions is added to the list of … open projects
05:17:37,217 GlobalWorkspaceModel - Project instructions is removed … Project was disposed.
```

IDE заходит на путь открытия проекта, обнаруживает дубликат и выбрасывает его через 180 мс, но окно
остаётся. Человек за машиной описал его так: «пустое окно вообще без какой-либо информации».

**Файлом — чисто.** `open "goland://open?file=<абсолютный путь>&line=1"` на стенде из двух проектов:

```
18:44:53 CommandLineProcessor - external URI request: goland://open?file=…/mcp-hub/zz-…-9f3a.md
18:44:53 BeforeFileOpenLoggerListener - beforeFileOpened zz-agent-watch-probe-9f3a.md
18:44:53 BeforeFileOpenLoggerListener - fileOpened zz-agent-watch-probe-9f3a.md
```

Имя файла было уникальным и существовало ровно в одном проекте, так что маршрутизация доказана:
**файл открывается в том проекте, которому принадлежит.** Ни нового окна, ни пустого окна —
число окон не изменилось. Приложение при этом выходит на передний план.

То есть провал первого замера был не свойством способа, а следствием того, что ему дали каталог.

**Схему регистрирует сама IDE, а не Toolbox.** В `Info.plist` GoLand есть `CFBundleURLSchemes:
["goland"]` под именем `Stacktrace`. Схему `jetbrains://` перехватывает **демон JetBrains**
(`jetbrainsd.app`), а не Toolbox, — это отдельная зависимость, и в её журнале видны обрывы
websocket. Продуктовая схема до демона не доходит вовсе.

**Чего `open` не делает.** Форма `jetbrains://goland/navigate/reference?project=<имя>` без пути не
делает ничего: URL доходит до демона, в журнале IDE — тишина. То есть «просто подними окно этого
проекта, ничего не открывая» готовой командой не выражается; файл открыть придётся.

**Файл попадает куда надо, но окно проекта не поднимается.** Это доказано и замером, и исходниками.

Замер на стенде из трёх открытых проектов, окна которых стоят стопкой на одном экране (Spaces тут ни
при чём — в системе по одному Space на монитор). Признак `kCGWindowIsOnscreen` показывает верхнее
окно: когда GoLand впереди, его окна поднимаются над чужими группой, стопка перекрывает сама себя, и
видимым остаётся ровно одно. Открывал по очереди файлы, принадлежащие трём разным проектам:

```
PROBE-project  -> frontApp=GoLand visibleGoLandWindows=[2429]
mcp-hub        -> frontApp=GoLand visibleGoLandWindows=[2429]
PROBE-project  -> frontApp=GoLand visibleGoLandWindows=[2429]
mcp-hub        -> frontApp=GoLand visibleGoLandWindows=[2429]
```

Окно одно и то же во всех случаях. Работай подъём — сменилось бы хотя бы раз; какое окно какому
проекту принадлежит, для этого вывода знать не нужно.

**Подтверждено глазами.** Отдельный совместный замер: человек сделал активным окно одного проекта и
открыл ссылкой файл из другого. Результат — «вкладка в нужном проекте, окно осталось прежним». То
есть маршрутизация верна, а нужное окно человек так и не увидел.

Исходники согласны. `CommandLineProcessor.findBestProject` перебирает открытые проекты и возвращает
тот, чей `BaseProjectDirectories` содержит файл, — вот откуда правильная маршрутизация. Но у этого
перебора есть запасной путь, и он опасен:

```kotlin
val project = IdeFocusManager.getGlobalInstance().lastFocusedFrame?.project
return if (project != null && !LightEdit.owns(project)) project else projects.first()
```

Если файл не принадлежит **ни одному** открытому проекту, он открывается вкладкой в том окне,
которое было активным. Наблюдено вживую: файл из проекта-пустышки оказался вкладкой в окне рабочего
проекта. Для перехода из виджета это значит, что перед вызовом надо убедиться, что проект открыт
(`recentProjects.xml` плюс «эта IDE запущена»), иначе переход мусорит вкладками в чужом проекте.

А вывод окна вперёд живёт в `processExternalCommandLine(args, currentDirectory, focusApp:
Boolean = false)`, и именно там стоит `WindowManager.getIdeFrame(result.project)` с
`AppIcon.requestFocus`. По умолчанию `focusApp` выключен.

Значит `open` даёт «файл открыт в нужном проекте, приложение впереди», но **не** «нужное окно
впереди». Для двух проектов в одном приложении это ровно та половина, которой не хватает.

### `open` можно научить своей команде

Это меняет устройство плагина, поэтому вынесено отдельно.

В платформе есть точка расширения `com.intellij.jbProtocolCommand`
(`platform/platform-impl/src/com/intellij/openapi/application/JBProtocolCommand.kt`). Плагин
регистрирует свою команду, и она становится доступна по ссылке вида

```text
jetbrains://<продукт>/<команда>/<цель>?параметры
```

Разбор адреса — в самой платформе: `parts[1]` это имя команды, `parts[2]` — цель, остальное
параметры запроса. Возвращаемое значение — `JBProtocolCommandResult(dialogMessage,
focusIdeWindow = true)`, то есть **вывод окна вперёд платформа берёт на себя** и по умолчанию делает
его. Точка расширения не экспериментальная: на ней работают штатные команды самой платформы. Их в
GoLand 2026.1 ровно три — `navigate`, `settings` и `checkout` из VCS; перечислено по jar-ам
установленной IDE. Команды установки плагина среди них нет, хотя прежняя редакция этого абзаца
называла её примером. Полезное следствие у перечисления всё же есть: команда `settings` берёт
параметр `name`, то есть `jetbrains://<продукт>/settings?name=Plugins` открывает страницу плагинов —
тем же транспортом человека можно довести до диалога установки.

**Замерено, а не выведено** (11 сентября 2026, GoLand 2026.1.4): после открытия этого адреса в
журнале IDE появляется `CommandLineProcessor - external URI request: jetbrains://goland/settings?
name=Plugins`, а сразу за ним — `MarketplaceRequests - Looking for the last compatible plugin
updates`, то есть открылась именно страница плагинов, а не просто окно настроек.

Следствие для устройства: **Unix-сокет плагину не нужен.** Agent Watch вызывает
`NSWorkspace.open(url)`, и это весь транспорт — ни портов, ни обнаружения, ни авторизации. Замерено
именно этим вызовом, а не через `open(1)` из терминала: `NSWorkspace.open` на
`jetbrains://goland/agent-watch/ping?token=…` вернул `true`, и плагин записал ответ с этим токеном.

Обойтись **продуктовой** схемой (`goland://agent-watch/focus?pid=N`) и не зависеть от демона не
вышло — проверено и опровергнуто: адрес доходит до `CommandLineProcessor` (строка в журнале есть),
но до команды плагина не доходит, файла-ответа нет. Демон JetBrains, таким образом, обязателен.
Живёт он в `~/Library/Application Support/JetBrains/Daemon/bundles/current/jetbrainsd.app`, и ставит
его не только Toolbox: в `lsregister` схему `jetbrains:` заявляют и демон, и Toolbox по отдельности,
а этот каталог заводит сама IDE. Значит, проверять наличие демона надо по этому пути, и это одно из
четырёх условий, при которых Agent Watch вообще открывает адрес.

### Где сессии живут на самом деле

Снимок в момент замера:

```
pid=9325  cwd=~/CommonProjects/agent-watch   claude ← zsh ← login ← ghostty(691)
pid=7761  cwd=~/CommonProjects/agent-watch   claude ← zsh ← login ← ghostty(691)
pid=1981  cwd=/                              codex  ← ChatGPT(688)
```

**Снимок не показателен, и это сказано человеком, а не выведено.** Незадолго до замера ноутбук
самопроизвольно перезагрузился, поэтому в терминалах IDE сессий не было ни одной. Обычное окружение —
**терминал JetBrains IDE**, он же самый частый; Ghostty идёт вторым. Это меняет расклад целиком:
основной хост словаря AppleScript не имеет.

Что снимок всё-таки доказывает и что от перезагрузки не зависит: **две сессии Claude в одном проекте
и одном приложении, в разных вкладках.** Точности «до проекта» не хватает — она не различила бы эту
пару строк в виджете. Требование сформулировано прямо: нужна точность до вкладки.

### Ключ связи уже написан агентом

Ghostty, спрошенный через AppleScript, называет свои вкладки так:

```
window tab-group-…7b10  tab 1 selected=true  terminal EA251683-… cwd=~/CommonProjects/agent-watch
    name = "◑ Следующие задачи по плану реализации"
window tab-group-…45a0  tab 1 selected=true  terminal 58E03558-… cwd=~/CommonProjects/agent-watch
    name = "✳ Объединение иконок тула и консоли"
```

А транскрипт первой из них содержит `"aiTitle": "Следующие задачи по плану реализации"` — ровно ту
строку, которую `SessionDescriptionResolver` уже вытаскивает и кладёт в имя сессии. Claude сам пишет
заголовок вкладки, добавляя к имени значок своего состояния.

Отсюда два следствия. Первое: рабочий каталог как ключ связи не годится — у обеих сессий он один и
тот же, — а имя годится, и оно уже есть в строке виджета. Второе: вариант «пусть hook переименовывает
вкладки» из прошлой редакции не нужен, эта работа уже сделана самим агентом.

### Точная вкладка достижима, и это проверено

Ghostty несёт полный словарь AppleScript: класс `terminal` со свойствами `name`, `working directory`,
`id`, `environment variables`, класс `tab` с `selected` и `index`, и команды `select tab`,
`activate window` и `focus` («Focus a terminal, bringing its window to the front»).

Замер: попросили `focus` для терминала другой сессии, затем вернули фокус обратно.

```
asked=[✳ Объединение иконок тула и консоли]
became=[✳ Объединение иконок тула и консоли]
restored=[◑ Следующие задачи по плану реализации]
```

Одним вызовом поднимается и окно, и вкладка. Это единственный проверенный на этой машине способ
довести до вкладки.

### Кто вообще поддаётся скриптованию

| Хост | Словарь AppleScript |
|---|---|
| Ghostty | есть, с `focus` до отдельного терминала |
| Terminal.app | есть (системный) |
| ChatGPT.app (хост Codex Desktop) | есть, но браузерного вида: окна и вкладки с `title` и `URL` |
| GoLand, PyCharm, IntelliJ IDEA, WebStorm, RustRover | нет |
| VS Code, Cursor, Zed | нет |

iTerm2 на машине не установлен; его словарь известен и умеет выбирать вкладку, но здесь это не замер.

**Для Codex Desktop потолок — уровень приложения, и это не вопрос замера.** Один процесс `codex` с
рабочим каталогом `/` держит все треды сразу, хуки Codex не несут номера процесса вообще (см.
`docs/agent-integration.md`), а словарь ChatGPT.app — типовой браузерный шаблон: окна и вкладки с
`title` и `URL`, без единого понятия о треде. Связать строку виджета с чем-то внутри приложения
нечем — ни ключа, ни адресуемой единицы. Пока OpenAI не даст deep link на локальный тред, для
половины продукта ответ — вариант B: назвать словами, что известно, и поднимать приложение.

### Терминал JetBrains: заголовок вкладки есть, но полагаться на показанный нельзя

Это основное окружение, поэтому разобрано отдельно. Источник — трекер JetBrains, а не догадки.

| Что | Состояние |
|---|---|
| `IDEA-277846` «Support changing terminal tab title by escape sequences» | Fixed, доступно с **2022.2** |
| `IJPL-241950` «no way to see full application title» | Fixed в **2026.1.1**: подсказка с полным заголовком |
| `IJPL-240838` вкладка не переименовывалась, пока скрипт работает | Fixed в **2026.1.2** и 2026.2 |
| `IJPL-237270` заголовок «излишне обрезается» в новом терминале | **открыт** |

Значит, заголовок из escape-последовательности терминал IDE понимает — тот самый, который Claude уже
пишет.

**И он доходит целиком — обрезка чисто зрительная.** Проверено на GoLand 2026.1.4 с четырьмя живыми
сессиями: вкладки терминала называются именем сессии, тем же, что стоит в строке виджета; у длинных
имён ярлык вкладки укорачивается, но сама строка остаётся полной. Это согласуется и с трекером, и с
платформой: починкой `IJPL-241950` стала **подсказка с полным заголовком** — то есть JetBrains
подтверждает, что укорочен только показ, — а `TerminalWidget.terminalTitle` отдаёт значение целиком.

Прошлая редакция этого документа считала обрезку потерей данных. Это была ошибка: теряется только
ширина ярлыка.

Опираться на имя как на единственный ключ всё равно не стоит, но причины остались другие:
поведением управляет настройка `Settings → Tools → Terminal → Show application title in tab name`,
которую человек может выключить, и два агента с одинаковым именем сессии дадут две одинаковые
вкладки.

Вывод для реализации: имя вкладки — **хороший запасной ключ и отличная подсказка человеку**, но
основным ключом остаётся номер процесса, который плагин берёт напрямую и который не зависит ни от
настроек, ни от того, что пишет агент.

### Что может плагин: проверено по исходникам платформы

`TerminalToolWindowManager` (`plugins/terminal/src/org/jetbrains/plugins/terminal/`) — публичный
класс с публичными методами:

```java
public static TerminalToolWindowManager getInstance(@NotNull Project project)
public @NotNull Set<TerminalWidget> getTerminalWidgets()
public ToolWindow getToolWindow()
```

`TerminalWidget` (`platform/execution-impl/src/com/intellij/terminal/ui/`) отдаёт всё нужное:

```kotlin
val terminalTitle: TerminalTitle      // полный заголовок, не обрезанный
val ttyConnector: TtyConnector?       // отсюда PtyProcess и его номер
fun getCurrentDirectory(): String?
fun requestFocus()
```

Вкладки терминала — это обычные `Content` в `ContentManager` окна инструментов, и выбор вкладки
делается `contentManager.setSelectedContent(content, true)` плюс `toolWindow.activate(null)`. Выбор
вкладки так и работает. А вот дорога до самой вкладки и до её оболочки оказалась другой: ставка на
«платформенный API десятилетней давности вместо экспериментального `TerminalToolWindowTabsManager`»,
которая стояла в этом абзаце, опровергнута замером — следующий раздел.

Отсюда ключ связи, который лучше любого заголовка: **номер процесса**. Agent Watch знает номер
процесса агента, плагин знает номер процесса оболочки во вкладке, и агент — потомок этой оболочки.
Ни имён, ни настроек, ни обрезки.

И главное свойство этого пути: **он не требует ни одного разрешения macOS**. Окно поднимает сама IDE,
своё собственное. Ни Accessibility, ни Automation, ни Screen Recording, и от подписи Agent Watch он
тоже не зависит.

### Переработанный терминал 2026.1: старый путь возвращает пустоту

Первый же запуск `focus` на живой IDE не нашёл ничего: в журнале `no terminal tab owns process 48814;
shells seen in open projects: []` — пустой список при трёх открытых вкладках с агентами. Причина
найдена не рассуждением, а чтением байт-кода установленной GoLand 2026.1 (`javap` по
`plugins/terminal/lib/`), и сходится из трёх независимых мест:

1. `TerminalOptionsProvider$State` заводит поле `terminalEngine` со значением `TerminalEngine.REWORKED`
   — переработанный движок стал умолчанием. В `options/terminal.xml` этой машины движок не задан,
   значит действует умолчание.
2. `TerminalToolWindowManager.findWidgetByContent(content)` — это одна строка:
   `content.getUserData(TERMINAL_WIDGET_KEY)`. А `TERMINAL_WIDGET_KEY` во всём плагине терминала
   записывает только сам `TerminalToolWindowManager`, то есть классический движок.
3. Модуль `intellij.terminal.frontend`, где живёт переработанный движок, **ни разу** не упоминает
   `com.intellij.terminal.ui.TerminalWidget` — ни одной ссылки ни в одном классе.

Вместе: у вкладки переработанного движка виджета нет, `findWidgetByContent` возвращает `null` для
каждой, и список оболочек пуст всегда. Это не редкий случай и не гонка при старте — это промах в ста
случаях из ста на стоковой 2026.1.

Рабочий путь — тот самый `TerminalToolWindowTabsManager`, который прошлая редакция отвергла:

```kotlin
TerminalToolWindowTabsManager.getInstance(project).tabs  // TerminalToolWindowTab
tab.content                                              // тот же Content, выбор вкладки не меняется
tab.view                                                 // TerminalView вместо TerminalWidget
tab.view.startupOptionsDeferred.await().pid              // номер процесса оболочки
```

Номер процесса он, вопреки прошлой записи, отдаёт — через `TerminalStartupOptions.pid`. Платформа
заполняет это поле оттуда же, откуда его брали мы: `TerminalSessionsManager.getLocalPid` разворачивает
соединение через `ShellTerminalWidget.getProcessTtyConnector` и берёт `process.pid()`. Ключ связи —
номер процесса — не изменился; сменился источник.

Три следствия для кода:

- **Спрашивать надо оба движка.** Движок — настройка (Settings | Tools | Terminal | Engine), её меняют
  на ходу, и вкладки, открытые до смены, остаются на прежнем движке. Ни один из двух списков сам по
  себе не полон.
- **`TerminalView` не умеет `requestFocus()`.** Он только называет компонент —
  `preferredFocusableComponent`, — а просит фокус платформа:
  `IdeFocusManager.getInstance(project).requestFocus(component, true)`.
- **Ждать `startupOptionsDeferred` нельзя.** Обход идёт по всем вкладкам всех открытых проектов, и
  вкладка, чья оболочка не запустилась, задержала бы всю команду. Читаем только завершённые
  (`isCompleted`) — у вкладки с работающим агентом оно завершилось давно.

Цена: весь этот API помечен `@ApiStatus.Experimental`. Это не «внутренний» (`@ApiStatus.Internal`),
плагину пользоваться им можно, но между релизами он вправе меняться. Стабильной замены нет: оболочка
переработанного движка живёт в сессии за представлением, и соединения с процессом на стороне вкладки
не существует вовсе. Первоначально переработанный путь был вынесен в отдельный файл и вызывался из-под
`catch (LinkageError)`. Проверка того варианта против GO-261.26222.72 дала `Compatible` и
27 использований experimental API. Она подтвердила зависимость от встроенного терминала,
но сама по себе не проверяла заявленную нижнюю границу 251.

**Уточнение по предрелизному ревью, 2026-09-12.** Настоящий прогон против GO-251.23774.430
выявил шесть ошибок совместимости и обращение к внутреннему enum: кроме классов нового
терминала, отсутствовали `PluginId.Companion` и getter настройки движка. Теперь новые классы
не входят в сигнатуры байткода: один адаптер разрешает семь точных публичных методов по именам
через classloader плагина. Отсутствующий или неполный API означает переход к классическим
вкладкам. Версия плагина читается из загруженного дескриптора, внутренний enum не используется.
Повторный `task plugin-verify` даёт `Compatible` и на 251, и на 261; отдельный тест проверяет
разрешение методов в настоящем API 261, поскольку verifier не проверяет строки рефлексии.
Ручной замер ниже относится к прежней версии; новая реализация проверена автоматически,
повторная проверка фокуса в работающих IDE остаётся отдельной проверкой.

Проверено и в работающей IDE. 0.1.2 поставлена из файла, GoLand перезапущена, `ping` ответил
`{"pluginVersion":"0.1.2","ideBuild":"GO-261.26222.72"}`. Затем `focus?pid=37664` при живой цепочке
`claude 37664 ← zsh 37489 ← goland 35517`: в журнале ни строки о промахе, окно IDE вышло вперёд,
выбралась вкладка нужного проекта, и каретка оказалась в терминале — последнее подтверждено
глазами, снаружи это не измеряется. То есть работают оба конца: и поиск вкладки у переработанного
движка, и фокус через `IdeFocusManager`.

### Обновление плагина из файла всегда просит перезапуск — так устроена платформа

Наблюдение: первая установка 0.1.0 загрузилась на ходу (`Plugin loaded/unloaded (re-load indexes)`
в журнале), а все три следующие — 0.1.1, 0.1.2, 0.1.3 — уехали в
`~/Library/Caches/JetBrains/GoLand2026.1/plugins/` вместе с `action.script` из двух команд, Delete и
Unzip, то есть до перезапуска.

Причина прочитана в байт-коде установленной IDE, `PluginInstaller.installFromDisk`
(`lib/intellij.platform.ide.impl.jar`, смещения 465–519). В переводе на Java:

```java
Path oldFile = (installed != null && !installed.isBundled()) ? installed.getPluginPath() : null;
boolean restartRequired = oldFile != null
                       || !DynamicPlugins.allowLoadUnloadWithoutRestart(descriptor)
                       || operation.isRestartRequired();
```

Первое условие закорачивает остальные: **если такой плагин уже установлен, установка из файла
требует перезапуска всегда**, и вопрос «а можно ли его выгрузить» даже не задаётся.

Гипотеза проверяема, и все три её предсказания сошлись:

| Предсказание | Наблюдение |
|---|---|
| первая установка идёт динамически | 0.1.0 загрузилась без перезапуска |
| любое обновление из файла — через перезапуск | 0.1.1, 0.1.2, 0.1.3, все три |
| `WARN` от `DynamicPlugins` не появится, до проверки не доходит | ни строки, хотя `LOG.warn` там безусловный |

Третье предсказание — самое ценное: причину отказа `allowLoadUnloadWithoutRestart` пишет
`LOG.warn(reason)` независимо от настроек категорий, поэтому её отсутствие означает не «не
настроили журнал», а «до проверки не дошли».

**Marketplace устроен иначе, и это важно для раздачи.** Путь обновления через окно плагинов —
`DefaultUiPluginManagerController.installOrUpdatePlugin` — зовёт
`PluginInstallOperation.setAllowInstallWithoutRestart(…)`, а дальше решает по
`DynamicPlugins.allowLoadUnloadWithoutRestart` и `PluginInstallOperation.isRestartRequired`. Условия
«уже установлен» там нет; отдельным случаем идёт только обновление встроенного плагина
(`isBundledUpdate`). То есть обновление из Marketplace перезапуска не требует, если плагин
выгружается, а наш, по данным Plugin Verifier, выгружаться должен.

Отсюда вывод для дневной работы: перезапуск, который мы наблюдаем, — свойство установки из файла, а
не нашего плагина, и починить его в плагине нельзя. Обходной путь для цикла полировки напрашивается
и **пока не проверен**: сначала Uninstall (выгрузка динамическая, если плагин выгружаем), потом
Install from Disk — тогда установленной копии нет, `oldFile` равен `null`, и ветка снова
динамическая.

### Ad-hoc подпись убивает любое разрешение на каждой сборке

Это то, что решает порядок работ, а не только выбор варианта.

```
ad-hoc:      designated => cdhash H"cb9d84357cb3395f18c59453c9d3dc7176cd84c5"
после пересборки без единой правки в исходниках:
             designated => cdhash H"03866db036acb974d9dd35185c33117bf28caeec"
```

TCC — база разрешений macOS — хранит рядом с разрешением требование к подписи заявителя. У ad-hoc
подписи это требование есть хеш конкретного двоичного файла, и он меняется от простого повторного
запуска `scripts/build-app.sh`. Значит, **любое** разрешение — Accessibility, Automation, Screen
Recording — теряется на каждом `task verify`, и вариант с разрешением нельзя даже испытать на себе.

Починка дешёвая и проверена: тот же бандл, подписанный настоящим сертификатом (взят самоподписанный
из связки ключей этой машины), даёт устойчивое требование —

```
A: designated => identifier "com.glockbender.agentwatch" and certificate leaf = H"f94aded4…"
B: designated => identifier "com.glockbender.agentwatch" and certificate leaf = H"f94aded4…"
```

— одинаковое до и после пересборки. То есть ждать Developer ID не нужно: локально созданного
сертификата хватает, чтобы разрешение пережило сборку. Developer ID нужен для раздачи, а не для того,
чтобы начать.

Теперь это заведено в сборку, и по дороге всплыла ловушка, стоившая бы часа. Свежесозданный
самоподписанный корень система считает **недоверенным** (`CSSMERR_TP_NOT_TRUSTED`), и
`security find-identity -v` его не показывает — флаг `-v` оставляет только доверенные. Но доверие
управляет *проверкой* подписи, а не её постановкой: замер прямой — `codesign --sign` с этим
сертификатом отработал с кодом 0 и дал требование
`identifier "com.glockbender.agentwatch" and certificate leaf = H"af226216…"`, одинаковое на двух
сборках подряд. Значит, помечать сертификат доверенным не нужно, а искать его надо без `-v`.

И проверено до конца, на настоящем разрешении. Выдали Automation на Ghostty, перешли к сессии из виджета — сработало.
Потом пересобрали приложение: бинарник изменился сам по себе, без единой правки в исходниках
(`9e87b033…` → `080ec6f2…`), то есть ровно тот случай, на котором под ad-hoc подписью разрешение
слетало. Запустили заново, перешли ещё раз — **сработало и разрешения больше не спросило**. Значит
свойство держится не на словах: сертификат сохраняет требование к подписи, а вместе с ним и
разрешения.

## Лестница точности

Задача распадается на ступени, и каждая покупает свою точность за свою цену.

0. **Приложение.** Как сейчас.
1. **Знать точно и сказать словами.** Без разрешений: карточка строки называет проект, окно и вкладку,
   даже когда прыгнуть туда нельзя.
2. **Вкладка в терминале IDE.** Плагин. Без разрешений macOS.
3. **Вкладка в скриптуемом терминале.** Automation, по разрешению на каждое приложение.
4. **Любое окно любого приложения.** Accessibility.

Ступени 2 и 3 не соперничают: у них разные хосты, и вместе они покрывают оба окружения, где сессии
живут. Ступень 4 нужна только там, где нет ни словаря, ни плагина.

## Варианты

### A. Как сейчас: поднять приложение

`NSRunningApplication.activate()`. Работает, ничего не требует, никогда не ошибается «не туда» —
просто не доводит. Для сегодняшних двух сессий в одном Ghostty не различает вообще ничего.

### B. Сказать словами, не прыгая

Собрать locator из того, что читается бесплатно (§ «Про сессию можно узнать всё»), и показать его в
карточке строки: проект, заголовок окна, имя вкладки. Переход остаётся на уровне приложения.

Этот вариант вырос после замера. Вкладка терминала в IDE носит **имя сессии** — ту же строку, что
стоит в строке виджета. Значит карточке достаточно сказать «GoLand, проект `mcp-hub`, вкладка
терминала с этим же именем», и человек находит её глазами за секунду, без единого разрешения и без
плагина. У длинных имён ярлык укорочен, поэтому обещать стоит совпадение начала, а не всей строки.

- **Плюсы:** ноль разрешений, ноль записи в чужие программы, удаляется вместе с приложением и не
  оставляет следов. Работает одинаково для всех хостов, включая Codex Desktop, где ничего другого
  нет. Две строки с одинаковым проектом перестают быть неразличимыми.
- **Минусы:** человек всё равно кликает сам. Имя вкладки можно выключить настройкой IDE, и два
  агента с одинаковым именем сессии дадут одинаковые вкладки.
- **Требует:** ничего.

### C. AppleScript до конкретной вкладки

Найти терминал по имени сессии и вызвать `focus`. Проверено на Ghostty.

**Сравнивать надо не на равенство.** Ghostty отдаёт `"◑ Следующие задачи по плану реализации"`, а в
транскрипте лежит `"Следующие задачи по плану реализации"`: Claude ставит перед именем значок своего
состояния, и значок меняется — в двух снятых образцах это `◑` и `✳`. Набор значков принадлежит агенту,
перечислять его у себя нельзя, поэтому правило — «имя вкладки заканчивается именем сессии», а не
«равно» ему. Совпадений должно быть ровно одно; два или ноль означают, что связать не удалось, и
переход падает на уровень приложения.

- **Плюсы:** **единственный проверенный способ довести до вкладки.** Один вызов поднимает и окно, и
  вкладку. Ключ связи уже есть — имя сессии в строке виджета. Разрешение узкое и адресное: «Agent
  Watch хочет управлять Ghostty», по приложению, а не на всю систему. Снимается одним переключателем
  и не оставляет ничего в чужих файлах.
- **Минусы:** только там, где есть словарь, — Ghostty, Terminal.app, iTerm2; в JetBrains, VS Code и
  Cursor словаря нет. Имена вкладок могут совпасть у двух сессий с одинаковым `aiTitle`. Пока имени
  сессии нет (первые минуты), совпадать не с чем — падаем на вариант A. Требует
  `NSAppleEventsUsageDescription` в `Info.plist`, иначе macOS откажет.
- **Требует:** устойчивую подпись (§ «Ad-hoc подпись»); разрешение Automation на каждый хост.

### D. Окно проекта в JetBrains через `open`

`open "goland://open?file=<файл в проекте>"`. Путь к файлу берётся из рабочего каталога агента
(`proc_pidinfo`), продукт — из родительской цепочки процессов. Ни Toolbox, ни `PATH`, ни портов, ни
демона: схему регистрирует сам бандл IDE.

- **Плюсы:** без разрешений и без плагина. Файл попадает в тот проект, которому принадлежит, —
  доказано уникальным именем. Лишних окон не появляется. Работает сегодня, кода на десяток строк.
- **Минусы:** **окно нужного проекта не поднимает** — доказано на трёх проектах, — так что при
  нескольких окнах человек нужного всё равно не увидит. Открывает файл, которого он не просил, то
  есть меняет состояние редактора ради навигации. До вкладки не доводит. Каталогом вместо файла
  вызывать нельзя ни в коем случае — будет пустое окно.
- **Требует:** выбрать, какой файл открыть. Разумный выбор — файл, который в этом проекте уже открыт
  (тогда видимого изменения меньше всего), иначе `README` или сам корневой файл проекта.

### E. Accessibility

Перечислить окна процесса, найти нужное, выполнить `kAXRaiseAction`. Тем же деревом можно дойти до
вкладок терминала IDE.

- **Плюсы:** единственный способ, не зависящий от того, есть ли у хоста словарь: одинаково работает
  для GoLand, VS Code и Cursor. Заголовок окна читается через AX и **не требует** Screen Recording.
- **Минусы:** самое широкое разрешение из всех — право читать содержимое чужих окон ради одного перехода.
  Дерево вкладок IDE не документировано и меняется с обновлениями. Запись в списке System Settings
  остаётся после удаления приложения, и убрать её приложение не может.
- **Требует:** устойчивую подпись; разрешение; аккуратный откат к варианту A, когда дерево не то.

### F. Плагин для IDE

Единственный путь до вкладки в основном окружении. Прошлая редакция отбрасывала его как «отдельный
продукт»; по исходникам платформы он оказался куда меньше.

Устройство целиком, и транспорт у него — тот же `open`. В платформе есть точка расширения
`com.intellij.jbProtocolCommand`: плагин регистрирует свою команду, Agent Watch вызывает
`NSWorkspace.open("jetbrains://goland/agent-watch/focus?pid=68554")`, и платформа сама разбирает
адрес, зовёт команду и выводит окно вперёд (`JBProtocolCommandResult.focusIdeWindow`, по умолчанию
`true`). Ни сокета, ни порта, ни обнаружения, ни авторизации.

Внутри команда перебирает `getTerminalWidgets()` всех открытых проектов, берёт у каждого номер
процесса оболочки через `ttyConnector`, находит тот, чьим потомком является агент, выбирает его
`Content` и активирует окно инструментов. Промахнуться нечем: совпадение либо есть, либо нет.

- **Плюсы:** **точность до вкладки в том окружении, где сессии живут чаще всего.** Ни одного
  разрешения macOS — окно поднимает сама IDE. Ключ связи — номер процесса, а не имя: ни настройки
  `Show application title`, ни обрезки заголовка, ни зависимости от того, что пишет агент. Не зависит
  от подписи Agent Watch, то есть не ждёт milestone раздачи. Один плагин работает во всех продуктах
  JetBrains: нужен только модуль платформы и бандленный `org.jetbrains.plugins.terminal`.
- **Минусы:** второй тулчейн в репозитории на Swift — Kotlin и Gradle. Плагин ставится копированием
  каталога в `~/Library/Application Support/JetBrains/<продукт>/plugins/`, и такой каталог IDE
  читает только на старте — то есть скопированный снаружи подхватится со следующего запуска.
  Точка расширения объявлена `dynamic="true"`, поэтому загрузка без перезапуска возможна, но
  через собственный диалог IDE «Install Plugin from Disk». Совместимость надо держать:
  `until-build` не проставлять, а сломаться API
  всё-таки может. Из перечисленного API экспериментален только `TerminalToolWindowTabsManager`,
  которым мы как раз не пользуемся, — но `TerminalWidget` и `ttyConnector` тоже не публичный
  контракт для сторонних плагинов.
- **Требует:** решения, что второй тулчейн приемлем.

Установка и удаление ложатся ровно в то, что приложение уже делает: окно тулинга пишет каталог
плагина рядом с продуктом — так же, как пишет хуки в `settings.json` агента, — и удаляет его тем же
рядом. Отличие одно, и его надо сказать словами в ряду: скопированный каталог вступает в силу со
следующего запуска IDE.

### Отвергнуто

- **Screen Recording ради заголовков окон.** Заголовки берутся из `recentProjects.xml` для JetBrains
  и из AppleScript для скриптуемых хостов; платить за них правом записи экрана незачем.
- **«Allow unsigned requests» во встроенном сервере IDE.** Это просьба к человеку ослабить **чужую**
  программу: порт начнёт отвечать любому процессу на машине, включая страницу в браузере. Вернуть
  настройку обратно Agent Watch не может.
- **Чтение `permanent.token` из чужого кэша.** Файла на машине нет, а сам приём — залезание в кэш
  другой программы.
- **Переименование вкладок через OSC.** Claude уже делает это сам.
- **Приватные функции подъёма окна** (`_SLPSSetFrontProcessWithOptions` и подобные). Недокументированы
  и ломаются молча.

## Рекомендация

**Плагин для JetBrains первым, AppleScript вторым, «сказать словами» всегда.** Порядок диктует
требование: нужна точность до вкладки, а чаще всего вкладка — это терминал IDE.

**Первый слой — вариант F, плагин, и транспортом к нему служит тот же `open`.** В основном окружении
он единственный, кто доводит до вкладки: словаря AppleScript у JetBrains нет, а прочитать вкладку
снаружи нечем — ни имени, ни дерева. Плагин цепляется за номер процесса, самый крепкий ключ, какой
бывает, и не просит ни одного разрешения macOS, потому что окно поднимает сама IDE. Он же
единственный вариант, который не ждёт ни подписи, ни milestone раздачи.

Своего сокета и сервера ему не нужно: команда регистрируется точкой расширения `jbProtocolCommand`
и вызывается ссылкой, так что со стороны Agent Watch это одна строка `NSWorkspace.open(url)`. Цена
честная и она одна: второй тулчейн, Kotlin и Gradle, в репозитории на Swift.

**Второй слой — вариант C, AppleScript.** Ghostty — второе по частоте окружение, и там всё уже
проверено: `focus` доводит до вкладки, ключ связи Claude пишет сам. Работа маленькая, эффект полный,
и она не пересекается с плагином — разные хосты. Terminal.app и iTerm2 добавляются тем же приёмом с
другим словарём.

**Ноль перед вторым слоем — подпись сертификатом, а не ad-hoc.** Нужна только варианту C: без неё
разрешение Automation отваливается на каждой сборке, и вариант нельзя даже испытать. Сертификат
создаётся локально, `build-app.sh` берёт его, если он есть, и падает на ad-hoc, если нет.

Границу стоит назвать сразу: локальный сертификат снимает блокировку **только на этой машине**.
Сборка, отданная другому человеку, снова ad-hoc, и у него разрешение будет отваливаться на каждом
обновлении — до Developer ID и нотаризации из milestone раздачи. То есть сертификат разблокирует
испытание на себе, а не выпуск функции. Плагина это не касается вовсе.

**Третий слой — вариант B, и он не запасной.** Карточка строки называет проект, окно и вкладку
независимо от того, поставлен ли плагин и разрешено ли что-нибудь. Работает без разрешений, честно
показывает доступную точность — чего требует `docs/architecture.md` §8 — и остаётся единственным, что
есть у Codex Desktop и у любого хоста без словаря и без плагина.

**Accessibility (E) — нет.** Для терминала IDE он проигрывает плагину по всем статьям: разрешение
самое широкое из существующих, дерево вкладок не документировано, читает он лишь **укороченный
ярлык** вкладки, а полноценное дерево Swing-приложения может потребовать включить в IDE
«Support screen readers» — то есть попросить человека изменить поведение его же редактора ради
нашего перехода. Смысл он приобретёт только тогда, когда ежедневным хостом станет что-то без
словаря и без плагина — VS Code, Cursor, Zed.

**`open` файлом (D) — нет, и это тоже доказано замером.** Он не плодит окон и правильно выбирает
проект, но нужное окно вперёд не выводит, а значит при нескольких окнах не решает даже задачу «до
проекта». Остаётся полезным как **транспорт**: той же ссылкой вызывается команда плагина, и вот там
подъёмом окна занимается уже плагин. Каталогом вместо файла не вызывать никогда.

## Где это настраивается

Окно тулинга, третий раздел рядом с агентами — `Focus`. Устройство то же, что у существующих рядов
(`docs/architecture.md` §8): ряд на хост, состояние одной фразой, и одна кнопка, чьё слово меняется
вместе с состоянием.

```text
Focus
  GoLand             Exact tab. Plugin installed, waiting for restart.   [Remove]
                     Writes ~/Library/…/JetBrains/GoLand2026.1/plugins/agent-watch
  PyCharm            Exact tab. Plugin not installed.                    [Install]
  Ghostty            Exact tab. Allowed.                                 [Revoke…]
  Terminal           Exact tab. Not asked yet.                           [Allow…]
  Cursor             Application only. No supported way to do better.
```

Ряды плагина устроены как ряды хуков и по той же причине: приложение пишет файл в чужую программу,
поэтому называет файл, называет состояние и даёт снять. Единственное отличие, которое надо сказать
словами прямо в ряду, — **вступает в силу со следующего запуска IDE**: каталог плагина IDE читает
только при старте. Загрузить сразу способна сама IDE — точка расширения динамическая, — но это её
диалог «Install Plugin from Disk», а не наша кнопка.

Четыре правила, которые стоит соблюсти.

**Разрешение спрашивается по нажатию, а не при запуске.** Диалог Automation появляется в первый раз,
когда человек кликнул по строке сессии в этом приложении, — то есть в момент, когда понятно, зачем он.
До этого приложение работает как сейчас.

**Ряд говорит, что останется после удаления.** У рядов с разрешением — фраза про запись в System
Settings и команду, которая её убирает. У рядов плагина — что каталог снимается этой же кнопкой. То
же правило, по которому ряды хуков называют файл, в который приложение пишет.

**Отказ — рабочее состояние, а не ошибка.** Человек без плагина и без Automation получает вариант B
и кнопку уровня приложения, и ряд говорит об этом словами, а не жалуется.

**Ряд появляется, когда хост появился.** Перечислять все IDE мира незачем: ряд заводится для того
приложения, в котором Agent Watch увидел хотя бы одну сессию.

## Открытые вопросы

Из шести вопросов прошлой редакции замером сняты четыре: точности «до проекта» не хватает, вкладки
переименовывать не нужно (Claude делает это сам), не-JetBrains окружение реально и второе по частоте,
а «Allow unsigned requests» отвергнут. Осталось три, и все три — решения, а не факты.

1. **Готовы ли завести второй тулчейн?** Плагин — это Kotlin и Gradle в репозитории на Swift. Отказ
   означает, что в основном окружении точность до вкладки недостижима: остаётся Accessibility со
   всеми его минусами или ступень «сказать словами».
2. **Выдавать ли Automation терминалу?** Нужно только варианту C. Разрешение узкое и адресное, но
   это всё же право посылать приложению команды. Отказ оставляет Ghostty на уровне приложения.
3. **Заводить ли локальный сертификат до Developer ID?** Нужен только варианту C. Альтернатива —
   ждать milestone раздачи. Плагина это не касается.

## Что уже собрано и чем это подтверждено

Набросок плагина написан и лежит в `ide-plugin/`. Что он снял с вопросов:

**API проверен по установленной IDE, а не по документации.** `javap` по банкам GoLand 2026.1:
`JBProtocolCommand.executeAndGetResult(target, parameters, fragment)` возвращает
`JBProtocolCommandResult(dialogMessage, focusIdeWindow)`;
`TerminalToolWindowManager.findWidgetByContent(content)` — статический метод, то есть путь от
вкладки к виджету есть, и перебирать надо `contentManager.contents`, а не `getTerminalWidgets()`,
у которого вкладка теряется; `TerminalWidget.getTtyConnector()` есть, а
`ProcessTtyConnector.getProcess()` даёт `java.lang.Process` и его номер;
`ProjectUtil.focusProjectWindow(project, boolean)` на месте.

**Перезапуск нужен не всегда.** Точка расширения объявлена так:

```xml
<extensionPoint name="jbProtocolCommand" interface="…JBProtocolCommand" dynamic="true"/>
```

Динамическая точка означает, что плагин загружается и выгружается без перезапуска — но делает это
сама IDE, когда плагин ставят её диалогом. Каталог, положенный снаружи, IDE читает на старте, так
что установка из окна тулинга вступит в силу со следующего запуска.

**Бандл плагина — это каталог с одной банкой, 13.5 КБ.** Ровно та же форма, что у тридцати
плагинов, уже стоящих в `~/Library/Application Support/JetBrains/GoLand2026.1/plugins/`. То есть
приложение может носить его с собой и класть само.

**Связь по номеру процесса проверена на живых процессах.** Подъём вверх по дереву делается
`ProcessHandle.parent()`, тестами покрыты прямой потомок, внук (форма, которую даёт оболочка),
направление обхода, чужой номер и предел глубины.

**Согласия на сторонний плагин в этой сборке не нашлось.** Ни записи в
`~/Library/Application Support/JetBrains/consentOptions/`, ни строки про third-party plugin в
ресурсах IDE. Это доказательство отсутствием, и окончательно закроется первой установкой.

## Что осталось померить

Это не выбор, а незакрытые факты. У каждого написано, чем он закрывается.

1. **Как ведёт себя `TerminalWidget.ttyConnector` в новом («Reworked») терминале.** Ключ связи
   плагина — номер процесса оболочки, и он берётся оттуда. Классический терминал и новый — разные
   реализации, а `IJPL-237270` показывает, что расходятся они не только в мелочах. Закрывается
   первым же наброском плагина: перечислить виджеты и напечатать номера процессов в обоих движках.
2. ~~**Доходит ли своя команда по продуктовой схеме,** `goland://agent-watch/focus?pid=N`, минуя
   демон JetBrains.~~ **Закрыто, ответ отрицательный.** Адрес доходит до `CommandLineProcessor`, но
   до команды плагина — нет: файла-ответа `ping` не появляется. Зависимость от демона остаётся, и её
   наличие приходится проверять отдельно, потому что без него адрес пропадает молча.
3. **Диалог Automation из самого Agent Watch.** Не проверен: замер требует системного диалога.
   Закрывается так — добавить `NSAppleEventsUsageDescription`, подписать сертификатом, кликнуть по строке и
   посмотреть на диалог и на то, что окажется в System Settings.
4. **Поднимает ли `ProjectUtil.focusProjectWindow` нужное окно из стопки.** Через `open` подъём не
   происходит вовсе (`focusApp` по умолчанию выключен), но плагин зовёт подъём сам и явно. Это
   обычный `toFront` внутри одного Space, так что ожидание положительное — но это ожидание, а не
   замер. Закрывается первым наброском плагина. **Самый важный из оставшихся замеров:** если окно не
   поднимается, точность до вкладки бесполезна, человек её не увидит.
5. **Насколько сильно укорачивается ярлык вкладки у длинных имён.** Сама строка полная, укорочен
   только показ, но `IJPL-237270` про избыточное укорачивание в новом терминале открыт. На выбор это
   не влияет — плагин связывает по номеру процесса, — но влияет на то, насколько внятной получится
   подсказка «ищи вкладку с таким именем».

## Где что будет жить

Разделение по `AGENTS.md` — первый вопрос, который задаст реализация, поэтому он записан здесь.

Разбор `product-info.json` — правило над байтами, которые прочитал кто-то другой, и проверяется без
диска. (Так же задумывался и разбор `recentProjects.xml`, и так он и был написан в `AgentWatchCore`;
сейчас его нет — см. примечание в начале документа.)

`NSWorkspace` и `NSAppleScript` — это `AgentWatchApp`. Подъём по дереву процессов и чтение
рабочего каталога по PID — `AgentWatchLookup`: обращения к ядру, Core их не берёт.

Плагин — отдельный каталог верхнего уровня со своим Gradle, и в сборку Swift он не входит. Сторона
Agent Watch — ещё одна `ToolingIntegration` рядом с хуками и статус-строкой: та же тройка «прочитать
состояние, записать, снять», тот же ряд в окне тулинга, и `ToolingReport` о нём уже умеет
рассказывать. Вызов ссылки — `NSWorkspace.open` — живёт в `AgentWatchApp`; правило «какой сессии
какой хост» — в `AgentWatchCore`.
