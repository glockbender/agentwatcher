# Тип ветки выбирает проверку, но не ниже пола

**Статус:** принято 2026-11-23.

До типов защита Git знала два класса веток, заданных в коде: обычные и защищённые (`main`,
`master`, основная ветка сервера и ветки из `mothership.protectedBranch`). Владелец попросил
настраиваемые типы веток: имя, шаблоны имени ветки и уровень проверки для принудительной отправки
(force push) и удаления ветки на сервере. Уровней четыре: `none` — окна нет, `click` — одно
подтверждение, `name` — подтверждение и ввод имени репозитория, `forbid` — отказ без окна. Как это
выглядит для человека — [«Типы веток»](../git-protection.md#типы-веток).

## Решение

- **Таблица одна на все репозитории.** Её пишет приложение в
  `~/Library/Application Support/AgentWatch/git-branch-types.json`, читает `AgentWatchGit`.
  Первый тип, у которого совпал шаблон, выбирает уровень.
- **Пол.** `main`, `master`, основная ветка сервера, ветки из `mothership.protectedBranch` и метки
  не опускаются ниже `name`. Тип может только поднять их до `forbid`.
- **`mothership.protectedBranch` только поднимает.** Ветка из списка получает `name`, если тип
  не требует большего.
- **Ветка без типа идёт прежним путём.** Удаление — одно подтверждение, принудительная отправка —
  подтверждение и имя репозитория. Без типов не меняется ничего.
- **Один уровень на обе операции.** Отдельные уровни для отправки и удаления не делаем.

## Почему пол, а не только таблица

Агент работает от того же пользователя, что и человек. Он может переписать файл таблицы, выполнить
`git config` в репозитории и поменять `HOME` в своей команде. Всё, что читается из файлов, агент
может ослабить. Пол задан в коде исполнителя: имена `main` и `master`, ответ сервера о его основной
ветке и метки агент не меняет. Поэтому гарантия — пол, а таблица — удобство.

По той же причине `mothership.protectedBranch` может только поднять уровень. Иначе строка
`git config` в руках агента сняла бы проверку.

`forbid` и окна для веток вне пола — не гарантия. Агент, который правит таблицу, может поставить
своей ветке `none`. Таблица защищает от ошибки агента, а не от агента, который решил обойти
проверку; от него защищает только пол.

## Почему `none` разрешён ниже прежнего поведения

Раньше любая принудительная отправка и любое удаление ветки показывали окно. `none` убирает окно
совсем, и это сознательное ослабление. Его выбирает человек для веток, которые агент создаёт и
переписывает сам: черновики, временные ветки. Окно на каждую такую отправку приучает нажимать не
читая. Пол оставляет окно там, где ошибка стоит дорого.

## Почему обработчик пропускает только доказанные ветки

При `none` обработчик пропускает команду `git push` агента, и исполнитель её не видит. Значит,
обработчик сам должен убедиться, что пол не задет:

- **Короткое имя может оказаться меткой.** `git push origin --delete topic` удалит метку `topic`,
  если на сервере есть такая метка. Обработчик пропускает имя `refs/heads/…`, локальную ветку без
  одноимённой метки или имя, которое известно как ветка сервера (`refs/remotes/<remote>/<name>`)
  и не совпадает с локальной меткой.
- **Основная ветка сервера бывает устаревшей локально.** `refs/remotes/origin/HEAD` мог не
  обновиться после смены основной ветки. Обработчик спрашивает сервер так же, как исполнитель
  (`git ls-remote --symref`, те же запреты на подмену адреса и транспорта), и читает
  `mothership.protectedBranch` тем же запросом `--local --includes`.
- **Любое сомнение — отказ с отсылкой к исполнителю.** Исполнитель знает точное назначение и
  выполняет `none` без окна. Агент получает лишний шаг, человек — ничего лишнего.

Остаётся одно окно: ветка удалена на сервере после последнего `git fetch`, и на её месте появилась
метка с тем же именем. Тогда `refs/remotes/<remote>/<name>` ещё указывает на ветку. Мы принимаем
этот риск: для него нужны устаревший `fetch`, тип `none` с подходящим шаблоном и метка, названная
как ветка.

## Почему ветка без типа не равна `click`

В брифе ветка без типа должна была вести себя как `click` и «как сейчас». Но сейчас принудительная
отправка в обычную ветку требует подтверждения и имени репозитория, а не одного нажатия: так
работал исполнитель и так проверяет тест `feature_push_still_requires_name`. Обе формулировки
вместе выполнить нельзя. Мы сохранили требование «без типов ничего не меняется»: оно в безопасную
сторону и проверяется старыми тестами без правок. Явный тип `click` даёт одно окно для обеих
операций.

## Почему файл через `HOME`, а нечитаемый файл — это «типов нет»

Агенты читают свои настройки через `HOME`, и `AgentWatchGit` запускается в их окружении.
Тестовое окружение с другим `HOME` получает свою таблицу, а без файла — прежнее поведение. Отладочная
копия приложения с `AGENT_WATCH_SUPPORT_DIR` пишет таблицу в свою папку, и `AgentWatchGit` её не
видит; это цена того, что исполнитель не зависит от переменной, которую выпускная сборка не читает.

Битый файл, неизвестная версия или неизвестный уровень означают «типов нет», а не ошибку. Ошибка
остановила бы и обычные проверки, а «типов нет» — это прежнее поведение, которое никогда не ниже
пола. Страница настроек показывает, что файл не читается.

## Отклонено

- **Таблица в конфигурации Git репозитория.** Её правит любая команда `git config` агента, и одна
  таблица на все репозитории — то, о чём просил владелец.
- **Отдельные уровни для отправки и удаления.** Владелец решил: один уровень на тип.
- **Типы для меток.** Шаблоны относятся к именам веток. Метки всегда на полу.
